model-router

Choosing the right model for each subagent, child session, or workflow agent shouldn't rely on guesswork. model-router applies a single written grid, routes spawns that don't specify a model yet, and measures on your machine how well each choice actually performs. Below, you'll find the core idea in plain terms first, followed by every detail of how it works.

In plain terms

When Claude Code delegates work to a subagent, it spins up a helper with a clean context to handle a single task and report back. Left on its own, though, the main agent launches every helper on its own model and at its own effort level—the amount of reasoning time allowed before answering.

That creates waste on both ends. A large model is expensive for a simple lookup that a small, cheap one could finish in seconds; conversely, handing a delicate review to an undersized model sends the work back and forces you to redo it.

model-router solves this with three mechanisms:

  • The grid: gives the agent a short written rulebook so it makes a deliberate choice before spawning a helper and states why.
  • The judge: catches helpers launched without an explicit model and classifies them on the fly.
  • Measurement: records, for each task class and combination of model and effort, how often work succeeds on the first try—first-pass yield—and what a good outcome actually costs.

Let's look at how the plugin's two components put this flow into practice.

How it works

model-router separates selection rules from automatic routing into two independent layers; the first works well even without the second.

  • The skill, model-router:choose-model. Loads whenever the agent is about to launch a subagent, child session, or workflow, and exposes the grid. The agent decides before spawning, passes model and effort explicitly, tags the description with the task class, and writes one line explaining the choice. Works even when mods are disabled.
  • The mod, model-router. When a subagent starts without a specified model, it queries the judge and sets both model and effort. Below each Agent call, it shows the model and effort actually assigned, logs every decision and outcome, and provides the /model-router command. Requires mods enabled and Claude Code 2.1.329 or later.

Not every spawn is touched: the router always respects choices already made and steps in only when the model is missing.

The spawnThe router
already specifies a model, or is a fork or resumekeeps it
names an agent whose definition pins a model, a plugin agent, or one whose definition cannot be readkeeps it
runs with routing disabled or with a session-wide subagent model pinned (CLAUDE_CODE_SUBAGENT_MODEL)keeps it
specifies no modelqueries the judge, then sets model and effort

The spawn call itself is never mutated: the model is applied when the subagent starts, and effort is applied on each of its model requests. Because of this, routing works under any permission mode, including auto mode. Among built-in subagent types, only general-purpose and Explore are routed.

Everything rests on clear, verifiable criteria—let's see how the grid is built.

The grid: how choices are made

To keep documentation, configuration, and behavior from drifting apart over time, the grid has a single machine-readable source: grid.json. The skill renders it in prose, the setup skill lists its values, and a test fails if the three ever diverge.

On every spawn, the first rule that yields a value wins:

  1. An explicit choice from you in the conversation.
  2. The project's ## Model routing section, when it names the kind of work or task class.
  3. An agent definition that pins its own model: the model stays unchanged and only effort is passed.
  4. The grid.

Model tiers

Scan the table from top to bottom and stop at the first row that fits the task.

Tier names are aliases: the concrete model mapped to each one depends on your configuration. From cheapest to most expensive: haiku < sonnet < opus < fable.

Effort

Answer these questions in order and stop at the first yes:

  1. Is it a simple task or a quick back-and-forth? → low
  2. Would an unnoticed mistake cost money, a customer, or a bad decision? → high
  3. Is it long, hard, and critical, and running unattended? All three must hold. → xhigh
  4. None of the above. → medium

The max level is never chosen.

Task classes

Every task falls into one of the six task classes below, each paired with a usual pick:

ClassCoversUsual pick

Put the task class at the start of the subagent description, such as [mr:read-search], or [mr:edit-specified!] if the spawn is risky. This tag is what tells measurement what kind of work the task belongs to.

Rules around the grid

Six practical principles round out the tables:

  • When in doubt, move up a tier. Handing work to a model that's too small costs more in rework than it saves.
  • Risk lives in the action, not the topic. Touching production, moving money, or altering unrecoverable data is risky; writing or testing code about those subjects is not. A risky spawn gets at least high effort and the ! marker.
  • Sessions: choose up front. Never switch the model of an already running session.
  • Escalate one step at a time. Retry first with sharper instructions; next, bump effort by one notch; finally, spawn at the next tier up with a handoff.
  • Coordinator model. A session that delegates most of the work runs on opus at medium effort, unless its own design work is complex.
  • Do it directly or delegate; follow up, don't restart. Handle a small task on files already in context within the current session; send a follow-up on the same topic to the subagent you already started.

Before every spawn, the agent states its pick on one line: 🔀, the model, a four-pip effort bar, the effort level, and the reason in under twelve words.

🔀 opus ▰▰▰▱ high -> review with unknown cause, going up
🔀 haiku ▰▱▱▱ low -> mechanical rename, easy to check

With the mod enabled, the same line appears in color beneath every Agent call, showing what the subagent actually received and why: explicit, fixed, judge: <class>; lowered from opus (or raised from, kept), judge: risky work; raised from <tier>, or keep: <why>.

That covers upfront choices. What happens, though, when a subagent launches with no model specified at all? That's where the judge comes in.

How the judge works

When a spawn arrives without a model and doesn't match any of the keep-as-is cases, a quick decision is needed before the subagent starts working. That job belongs to the judge, an internal classifier inside the mod that you never call directly.

What it receives

The judge receives the subagent type, the short description, and the first 4,000 characters of the task. To prevent prompt injection, the task text is wrapped as data, any internal closing tags are escaped, and the judge is instructed not to follow instructions found inside the text.

Its prompt

The prompt is generated directly from grid.json: it includes the tiers mapped to fast, balanced, and deep, the four effort questions numbered 0 through 3, the six task classes, and the rule that risk depends on the action. If you edit the grid, the judge's prompt updates automatically.

The call

The router makes a single call to the fast tier (the fastModel option, defaulting to haiku) at low effort, capped at 300 output tokens with an 8-second timeout (timeoutMs). The request runs through your session's client like a regular subagent and counts toward session cost.

The response

The judge returns a single JSON object:

{ "tier": "fast | balanced | deep", "confidence": 0.0, "effort": 0, "effort_confidence": 0.0, "risky": 0.0, "class": "<class>" }

What the router does with it

Undershooting ruins the output; overshooting just costs a little extra. For that reason, the router's thresholds are asymmetric:

RuleDefaultWhy
Lowering the model requires confidence ≥0.6getting it wrong underpowers the task
Raising the model requires confidence ≥0.3getting it wrong only costs money
risky above threshold, or ! tag0.7forces the deep tier and at least high effort, bypassing both thresholds
Missing confidence—never changes the model in either direction

Comparisons are always made against the parent session's model. Effort likewise changes only when its confidence clears the threshold: low requires the downgrade threshold, while higher levels require the upgrade threshold. If the call already carries an effort level, it is kept, and max is never set. Also, the judge's tiers top out at opus, so the router never picks fable.

When it fails

On error, the router fails open. A judge failure, timeout, or unreadable response leaves the spawn untouched and logs an error—except when a spawn is marked with !, which still moves up to the deep tier. Every decision is recorded with its action: downgrade, upgrade, keep, explicit, forced-risk, or error.

The defaults handle everyday work well, but every project has its own exceptions and sweet spots—let's see how to configure them.

Configuration

You can customize model-router at two distinct levels: repository-specific exceptions and global plugin options.

Project exceptions: the Model routing section

The grid stays the same everywhere; anything that varies from project to project belongs in the ## Model routing section of the repository's AGENTS.md (or CLAUDE.md).

To create or update it, ask to "set up model routing for this project" or state the rule you want right away, such as "always use opus for migrations." model-router:setup locates your instructions file, asks about defaults and exceptions, suggests a few by reading the repository, shows you the exact block, and writes it only after an explicit yes—without committing.

Once routing is active, the key question remains: are those picks paying off on your actual work? Here is how model-router turns session events into statistics.

How statistics are collected

Grading a subagent's quality without calling another model requires objective signals drawn from real work. model-router collects those signals locally and aggregates them only once it has enough information to close out a task.

Events

The mod appends records to events.jsonl inside your configuration directory without ever calling a model for measurement. Each line logs one of these events:

  • decision: every routing decision;
  • spawn: every subagent launch, with type, name, and short description;
  • signal: files written by the session and its subagents, failed tool calls, prompts you type, interrupts, and resumes;
  • report: each subagent's report, complete with tokens and estimated cost;
  • session-end: when the session closes.

Tasks and outcomes

Every subagent spawn corresponds to one task. Its outcome is locked in once the rework window expires: 30 minutes after the subagent reports back, or at session end if that comes first.

OutcomeWhen
successthe subagent delivered its report and nothing redid its work within the window
reworkwithin the window, the main session or another agent rewrote one of its files; a similar spawn of the same class followed; or one of your next two prompts named its files or task
failureit failed, or was stopped by the parent session and redone
cancelledno report arrived (an unresponsive task closes after 24 hours), or it was stopped

Two descriptions count as "similar" when the distinct words they share make up at least half of all their distinct words, ignoring common stop words and the task class tag.

Cells, metrics, and decay

Outcomes roll up into task class × tier × effort cells—for example, edit-specified · sonnet · medium. Each cell computes four metrics:

  • First-pass yield (FPY): success ÷ (success + rework + failure), i.e., how often work succeeded right away (see First-pass yield);
  • rework rate: rework ÷ (success + rework + failure);
  • cost per task: average estimated cost, taken from the engine's own estimate;
  • cost per successful task: cost per task ÷ FPY. A cheap model that often misses can end up with a higher cost per successful task than a pricier one.

Aggregated data decays with a 30-day half-life (halfLifeDays): work from a month ago carries half the weight of work done today. Statistics are maintained at two levels: user (you across all projects) and project (identified by its git remote, or falling back to its root directory).

Not everything feeds into recommendations and learning, though:

  • Excluded from learning: cancelled tasks, risky tasks, untagged tasks without a task class, tasks run on models outside the four families, and tasks without a known effort are logged, but never used for learning.
  • Weak signals: read-only task classes and cells with fewer than five tasks produce weak signals and are flagged accordingly.
  • Recommended cell: for each task class, the cell with the lowest cost per successful task among cells with at least three tasks, never dropping below the grid for review-debug and design-open. Through version 0.3 this is informational only: the router does not alter its picks based on it.

Compaction

Raw events stay open until the rework window closes. Compaction finalizes expired tasks, appends their outcomes, and folds them into the aggregates. It runs at session startup, whenever you open or refresh the usage view, and before generating the report; running it repeatedly is safe because no task is ever counted twice.

Among all the metrics collected, one sits at the heart of the entire system: first-pass yield.

First-pass yield: the number behind every choice

A cheap model that keeps getting things wrong doesn't save money—it makes you pay twice for the same job. First-pass yield (FPY) comes straight from manufacturing to measure this exact effect. On an assembly line, it tracks the share of units that come out right the first time, with no rework or scrap: at 95% FPY, one unit in twenty has to be redone or thrown away, and a reworked unit never counts as a first-pass success.

model-router applies the same logic to subagents. Every spawn is a unit: it passes on the first try if nothing had to redo its work over the next half hour.

How it is calculated

For each cell (task class × tier × effort, such as edit-specified · haiku · low):

FPY = success ÷ (success + rework + failure)

  • success counts toward FPY; rework and failure count against it. Outcomes follow the rules explained in How statistics are collected.
  • cancelled tasks stay out of both numerator and denominator: a task you stopped yourself, or one that never responded, says nothing about whether the model was up to the job.
  • Counts are time-weighted before dividing: with a 30-day half-life, a success from a month ago counts as half a success. FPY therefore reflects how models perform on your work today, not months ago.

Why FPY instead of price alone

A price sheet tells you what it costs to run a task, not what it costs to get a successful one. Work that comes back gets paid for all over again: in the retry, in the main session fixing it up, and in your own time. FPY converts raw price into the number that actually matters, cost per successful task:

cost per successful task = cost per task ÷ FPY

Compare two cells on the same kind of work, with twenty closed tasks each:

Cellsuccess / rework / failureFPYCost per taskCost per successful task
haiku · low5 / 12 / 325%$0.020$0.080
sonnet · low18 / 2 / 090%$0.050$0.056

Haiku costs less than half as much per individual run, yet every good result ends up costing more because three out of four tasks come back for rework. And the table is still generous: those fifteen redone tasks also burned main-session tokens and your own time, neither of which shows up on any price sheet. The flip side holds too: on a straightforward search, a small model nails it nineteen times out of twenty, so paying for a bigger one buys you nothing.

How to read it

  • The Overview tile shows 🟢 from 85% up, 🟡 from 70%, and 🔴 below that. Per-tier and per-effort bars use the same color scale.
  • Rework rate is the flip side of FPY: rework ÷ (success + rework + failure). Together, the two add up to 100% minus the failure rate.
  • A cell with fewer than five tasks is a weak signal (⚪): 100% across two tasks is luck, not statistics.
  • FPY is also marked weak for read-only task classes (read-search, read-analyze). Readers don't write files, so the strongest rework signal—someone editing those same files right afterward—never fires, making a poor search look like a success.
  • Automated signals can misread things: if you edit a file written by a subagent for reasons unrelated to its task, that edit still counts as rework. Across many tasks the noise averages out; across a handful it doesn't, which is why small cells remain marked weak.

How the router uses it

Today (versions 0.2 and 0.3), FPY informs rather than steers. The adapt option is off and the router strictly follows the grid. FPY powers the tiles and bars in /model-router, the report, and—for each task class—a recommended cell: the lowest cost per successful task among cells with at least three tasks, never below the grid for review-debug and design-open. When a recommendation consistently diverges from the grid, you can step in and add an exception to the project's ## Model routing section.

Starting in version 0.4 (planned), FPY will steer choices. With adapt enabled, the router tracks not a single FPY point estimate per cell, but a range of plausible values modeled as a Beta distribution: alpha grows with time-weighted successes, beta with weighted reworks and failures. On each subagent spawn, it draws a plausible FPY from each candidate cell neighboring the grid's pick, divides the cell's cost by that draw, and picks the lowest cost per successful task. This is Thompson sampling:

  • A cell with plenty of data draws values tightly clustered around its measured FPY, so a proven winner keeps winning.
  • A cell with sparse data draws widely spread values, so every now and then it wins the draw and gets tested. That exploration tapers off automatically as evidence accumulates, and is capped at 10% of decisions per task class (exploreCap).
  • Before any data arrives, the grid's pick starts ahead (alpha = 2, beta = 1, an expected FPY of two-thirds) while neighboring cells start even (1, 1): the grid wins until the numbers prove otherwise.
  • A project starts from your user-level record weighted as five tasks (projectPriorStrength); as it accumulates tasks of its own, its own record takes over.
  • Exploration never drops below the grid for review-debug and design-open, never drops below the project's ## Model routing defaults, and never touches risky spawns, which are measured but excluded from learning.

Why measurement comes first. Versions 0.2 and 0.3 only measure so you can check in /model-router that the signals make sense for how you work before handing over automated decisions.

Now that you know how to read the numbers, let's walk through the few steps needed to make them show up on your machine.

Getting statistics to show up

Seeing your first numbers takes no special setup, just five conditions in sequence:

  1. Enable mods and run Claude Code 2.1.329 or later. If /model-router comes back as an unknown command, the mod isn't loaded.
  2. Leave measure enabled. It is on by default.
  3. Run subagents. Only subagent spawns become tasks. Tag spawns when you write them by hand: an untagged spawn that bypasses the judge has no task class and won't be used for learning.
  4. Wait for the rework window to close. A task is tallied 30 minutes after its report, or once the session ends.
  5. Open /model-router, or ask for the model-router report. Opening the view runs compaction for up to 3 seconds; press r to refresh.

Once your first tasks close, you can inspect everything either in the terminal or in your browser.

The usage view and the report

Checking metrics shouldn't clutter your conversation or burn context tokens. Accordingly, /model-router opens a dialog styled like Claude Code's settings, with four tabs, a time window (24h, 7d, 30d, all), and a scope (user or project). What you see stays on your screen—the model never reads it.

  • Cost per successful task: 🟢 cheaper or 🔴 pricier than the previous window;
  • Rework: 🟢 up to 10%, 🟡 up to 25%, 🔴 above;

If you prefer a wider layout, the report page presents the exact same numbers—computed from the same aggregation—alongside weekly trends and a card for each task class. It is written to <config dir>/model-router/report.html and opened locally.

Two practical topics remain before you dive in: where your data is stored and the current version's limitations.

Privacy

The plugin never sends anything it measures anywhere. All files stay local inside model-router/ under your active configuration directory (CLAUDE_CONFIG_DIR, or ~/.claude otherwise):

  • the event log, which retains the first 2,000 characters of prompts you type;
  • the options used during compaction;
  • user- and project-level aggregates;
  • the report page.

Nothing is ever written inside your repositories. The only outbound call—the judge request on each routed spawn—goes to your model provider just like any other request in your session. To turn logging off, set measure: false; to wipe collected data, delete <config dir>/model-router/.

Limitations

Keep four limitations of the current version in mind:

  • Only spawns made through the Agent tool are routed; plugin-internal agents and workflow agents are measured, but not routed.
  • The router never selects fable and, through version 0.3, does not enforce the grid floor for review-debug and design-open.
  • Costs are engine estimates. Edits made outside the session's tools are not detected.
  • Through 0.3, data is only measured, never used to make decisions. Adaptive selection driven by quality data is planned for 0.4.
