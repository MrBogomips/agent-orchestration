model-router

Choosing the right model for every subagent, child session, or workflow agent should not be guesswork. model-router applies a single written grid, routes launches that do not yet specify a model on the fly, and measures on your machine how well each choice actually paid off.

In plain terms

When Claude Code delegates part of the work to a subagent, it starts a helper with a clean context that performs a single task and reports back. Left alone, however, the main agent launches every helper using its own model and effort level — how long the model thinks before answering.

The result is waste in both directions:

  • using a large, expensive model for a trivial file search that a fast model would finish in a moment;
  • handing a delicate review to a model that is too light, getting back an imprecise result that comes back to be redone.

model-router tackles the problem with three complementary mechanisms:

  • The grid: a short written rulebook that lets the agent choose deliberately before launching a helper and state its reason.
  • The judge: a fast classifier that catches helpers launched without an explicit model and assigns one on the fly.
  • Measurement: a local system that records, for every task class and model-and-effort combination, how often the work succeeds on the first try — first-pass yield — and what a good result actually costs.

Here is how the plugin's two layers put this flow into practice.

How it works

model-router separates the selection rules from automatic routing into two independent layers: the first works well on its own.

  • The skill (model-router:choose-model): loads whenever the agent is about to launch a subagent, a child session, or a workflow, and presents the grid. The agent decides before launching, passes model and effort explicitly, tags the description with the task class, and prints one line explaining the choice. Works even with mods turned off.
  • The mod (model-router): steps in when a subagent starts without a model specified, calls the judge, and applies model and effort. It also displays the actual assigned values beneath each Agent call, records decisions and outcomes locally, and enables the /model-router command. Requires mods enabled and Claude Code 2.1.329 or later.

The router never overrides an explicit choice: it only intervenes when the model is missing.

The launchRouter behavior
Already specifies a model, is a fork, or is a resumeKeeps it

Runs with routing turned off or with a session-level subagent model set (CLAUDE_CODE_SUBAGENT_MODEL)Keeps it

One important architectural detail: the launch call itself is never altered. The model is applied when the subagent starts, and effort is applied to each of its model requests. Because of this approach, routing works in every permission mode, including auto mode. Among built-in subagent types, only general-purpose and Explore are routed.

Now let's look at the criteria behind the grid.

The grid: how choices are made

To keep documentation, configuration, and behavior from drifting apart over time, the grid has a single machine-readable source: grid.json. The skill presents it in words, the setup skill lists its values, and an automated test fails if the three versions diverge.

At every launch, the first rule in priority order that produces a value wins:

  1. Your explicit choice in the conversation.
  2. The project's ## Model routing section, if it names that kind of work or task class.
  3. An agent definition that fixes its own model (in which case the model stays unchanged and only effort is passed).
  4. The grid.

Model tiers

Scan the table from top to bottom and stop at the first row that fits the task:

TierFits whenExamples
haikuSimple, repetitive work that is easy to check and requires no judgment callsListing or summarizing files; running a single command; renaming a symbol
sonnetThe expected result can be described clearly in one sentenceA well-specified edit across a few files; tests for existing code
fableBroad and open-ended work where judgment and precision truly matter (both conditions must hold)A complex design; an architectural decision with long-term consequences
opusEverything else, and whenever you are unsure between two tiersA review; debugging when the cause is unknown; most coordination work

Tier names are aliases: the concrete model mapped to each depends on your configuration. In ascending order of price: haiku < sonnet < opus < fable.

Effort

Answer the four questions in order and stop at the first yes:

  1. Is it a simple task or a quick exchange? → low
  2. Would an unseen mistake cost money, a customer, or a bad decision? → high
  3. Is it long, hard, and critical, and running unsupervised? (All three conditions must hold) → xhigh
  4. None of the above → medium

The max level is never chosen.

Task classes

Every task falls into one of six fixed task classes, each paired with a usual choice:

ClassCoversUsual choice
read-searchFinding files, symbols, or informationhaiku · low
read-analyzeReading and drawing conclusions: explaining, comparing, summarizingsonnet · medium
edit-mechanicalRepetitive edits that are easy to verifyhaiku · low
edit-specifiedAn edit whose end state fits in one sentencesonnet · medium
review-debugReview, or debugging with an unknown causeopus · medium
design-openOpen-ended design where judgment mattersfable · high

Place the task class at the start of the subagent description, such as [mr:read-search], or [mr:edit-specified!] when the launch is risky. This tag is what allows the statistics to classify every task.

Rules around the grid

Six practical principles complete the tables:

  • When in doubt, step up a tier. Giving work to a model that is too small costs more in rework than it saves.
  • Risk is in the action, not the topic. Touching production, moving money, or altering unrecoverable data is risky; writing or testing code that deals with those topics is not. A risky launch receives at least high effort and the ! marker.
  • Sessions: choose at the start. A running session's model is never changed.
  • Escalate one step at a time. Retry first with clearer instructions; then raise effort by one step; finally launch at the next tier with a handoff.
  • The coordinator's model. A session that delegates most of its work runs on opus at medium effort, unless its own design work is complex.
  • Do it directly or delegate; continue, don't restart. A small task on files already in context belongs in the current session; a follow-up request on the same topic goes to the subagent already running.

Before each launch, the agent states its choice on one line — the 🔀 symbol, model, four-slot effort bar, effort level, and reason in under twelve words:

🔀 opus ▰▰▰▱ high -> review with unknown cause, going up
🔀 haiku ▰▱▱▱ low -> mechanical rename, easy to check

With the mod enabled, the same line appears in color beneath every Agent call, showing what the subagent actually received and why (explicit, fixed, judge: <class>; lowered from opus / raised from / kept, judge: risky work; raised from <tier>, or keep: <why>).

So far we have seen choices made up front. What happens when a subagent launches with no model specified? That is where the judge comes in.

How the judge works

When a launch arrives with no model and does not match any of the kept cases, a fast classification is needed before the subagent starts working. That is handled by the judge, an internal classifier inside the mod that you never call directly.

What it receives and how the prompt is built

The judge receives the subagent type, its short description, and the first 4,000 characters of the task. To prevent interference (prompt injection), the task text is wrapped as data, any internal closing tags are escaped, and the judge is explicitly instructed not to execute any instructions contained in the text.

The system prompt is built directly from grid.json: it includes the three tiers handled by the judge (fast, balanced, deep), the four effort questions numbered 0 to 3, the six task classes, and the rule that risk depends on the action. If you edit the grid, the judge's prompt updates accordingly.

The call and the response

The router makes a single call to the fast tier (option fastModel, defaulting to haiku), at low effort, with a 300-token output cap and an 8-second timeout (timeoutMs). The call goes through your session's client like a normal subagent and counts toward the session cost.

The judge returns a single JSON object:

{ "tier": "fast | balanced | deep", "confidence": 0.0, "effort": 0, "effort_confidence": 0.0, "risky": 0.0, "class": "<class>" }

How the router decides

Aiming too low ruins the result; aiming too high only costs a bit more. That is why the decision thresholds are asymmetric:

RuleDefaultWhy
Lowering the model requires confidence ≥0.6Being wrong means giving the task too little
Raising the model requires confidence ≥0.3Being wrong only costs money
risky above threshold, or ! tag0.7Forces the deep tier and at least high effort, ignoring both thresholds
Missing confidence—Never changes the model, in either direction

The comparison is always against the parent session's model. Effort also changes only when effort_confidence clears its threshold (the downgrade threshold for low, the upgrade threshold for higher levels). If the call already carries an explicit effort, it is kept, and max is never set. Finally, the judge's tiers top out at deep (opus), so the router never picks fable.

When it fails

The router fails open. A judge failure, a timeout, or an unreadable response leaves the launch unchanged and logs an error; the one exception is a launch tagged with !, which still moves up to the deep tier. Every decision is recorded with its action: downgrade, upgrade, keep, explicit, forced-risk, or error.

The defaults work well in most cases, but every repository has its own exceptions: here is how to configure them.

Configuration

You can customize model-router at two distinct levels: single-project exceptions and global plugin options.

Project exceptions: the Model routing section

The grid stays the same everywhere; what varies from one repository to another goes into the ## Model routing section of the project's AGENTS.md (or CLAUDE.md) file.

To create or update it, ask "configure model routing for this project" or state the rule you want right away (for example, "always use opus for migrations"). model-router:setup locates the instruction file, asks you for defaults and exceptions, suggests a few by analyzing the repository, shows you the exact block, and writes it only after your explicit confirmation, without committing.

## Model routing

Defaults for `model-router:choose-model`. An explicit choice in the conversation still wins; anything not
listed here follows the grid.

- Default: the grid
- Coordinator: `opus` · `medium`

|---|---|---|---|---|
| Database migrations | `edit-specified` | `opus` | `high` | data cannot be restored |
| Bulk renames across the codebase | `edit-mechanical` | `haiku` | `low` | checked by the compiler |

All values must stay within the bounds of the grid: models haiku, sonnet, fable, opus; effort from low to xhigh; the six task classes. If you enter an out-of-list value, it is flagged along with the closest valid alternative.

Once routing is active, the key question remains: are the choices paying off on your real work? Here is how model-router turns session events into statistics.

How statistics are collected

Measuring a subagent's quality without asking a second model requires objective signals drawn from daily work. model-router collects these signals locally and closes each task's count only when it has enough evidence to evaluate the outcome.

1. Events

The mod appends records to events.jsonl inside the Claude Code config directory, without ever calling external models to measure. Each line records one of these events:

  • decision: every routing decision;
  • spawn: every subagent launch, with type, name, and short description;
  • signal: files written by the session and subagents, failed tool calls, prompts you type, interruptions, and resumes;
  • report: each subagent's report, complete with tokens and estimated cost;
  • session-end: the closing of the session.

2. Tasks and outcomes

Every subagent launch corresponds to a task. Its outcome is settled when the rework window expires: 30 minutes after the subagent's report, or at the end of the session if that comes first.

OutcomeWhen it is assigned
successThe subagent delivered its report and nothing within the window redid its work
reworkWithin the window, the main session or another agent rewrote one of its files; or a similar launch of the same class followed; or one of the next two prompts you typed named its files or task
failureThe subagent failed, or was stopped by the parent session and redone
cancelledNo report (a task that never responds closes after 24 hours), or interrupted

Two descriptions count as "similar" when the distinct words they share are at least half of all their distinct words (the similarityThreshold threshold), ignoring common words and the task class tag.

3. Cells, decay, and compaction

Outcomes flow into cells of the form task class × tier × effort — for example edit-specified · sonnet · medium — maintained at two levels: user (all your projects) and project (identified by the git remote or, failing that, the root directory).

  • Time decay: counts decay with a 30-day half-life (halfLifeDays), so work from a month ago weighs half as much as today's.
  • Exclusions from learning: cancelled tasks, risky tasks, tasks without a task class, tasks on models outside the four families, and tasks with unknown effort are recorded, but not used for learning.
  • Compaction: raw events remain open until the rework window closes. Compaction closes expired tasks and updates aggregates at session start, when you open or refresh the usage view, and before generating the report; repeating it is idempotent, because no task is ever counted twice.

Each cell computes four indicators: first-pass yield (FPY), rework rate, cost per task (engine estimate), and cost per successful task. One of them is the linchpin of the entire system: here is why.

First-pass yield: the number behind every choice

A cheap model that often gets things wrong does not save money: it makes you pay twice for the same work. First-pass yield (FPY) comes from manufacturing precisely to measure this effect: on a production line, it indicates the share of units that come out right on the first pass, with no rework or scrap. At 95% FPY, one unit in twenty has to be redone or discarded, and a reworked unit never counts as good on the first pass.

model-router applies the same principle to subagents: every launch is a unit, and it succeeded on the first pass if nothing had to redo it in the half hour that followed.

How it is calculated

For each cell (task class × tier × effort), using time-weighted counts:

FPY = success ÷ (success + rework + failure)

  • success counts in favor; rework and failure count against.
  • cancelled tasks are excluded from both terms: a task you stopped or that never finished says nothing about how well the model fit.
  • Thanks to the 30-day half-life, FPY reflects how models perform on your work today, not months ago.

Why FPY and not price alone

The price list tells you what it costs to run a task, not what it costs to get a successful one. Work that comes back is paid for again — in the second attempt, in the main session fixing it, and in your own time. FPY turns the price list into the number that actually matters, cost per successful task:

cost per successful task = cost per task ÷ FPY

Compare two cells on the same kind of work, with twenty closed tasks each:

Cellsuccess / rework / failureFPYCost per taskCost per successful task
haiku · low5 / 12 / 325%$0.020$0.080
sonnet · low18 / 2 / 090%$0.050$0.056

haiku costs less than half as much per launch, yet each valid result costs more because three tasks out of four come back. And the table is even optimistic, because it does not count the parent session's time or yours. The reverse holds too: for a simple search, a small model gets it right nineteen times out of twenty, and paying for a larger one brings no benefit.

How to read it

  • Color thresholds: in Overview, the FPY tile is 🟢 from 85%, 🟡 from 70%, 🔴 below; the tier and effort bars use the same scale.
  • Rework rate: the flip side of FPY (rework ÷ (success + rework + failure)). Together they add up to 100% minus the failure rate.
  • Weak signals (⚪): a cell with fewer than five tasks is marked weak — 100% across two tasks is luck, not statistics.
  • Read-only classes: read-search and read-analyze are also always marked weak. Readers do not write files, so the strongest rework signal (someone rewriting the same files right afterward) never fires, and a poor search tends to look like a success.
  • Inherent noise: if you edit a file written by a subagent for reasons unrelated to its task, that work is counted as rework. Over large numbers the noise evens out; over small numbers it does not, which is another reason to treat small cells as hints only.

How the router uses it

Today (versions 0.2 and 0.3), FPY informs rather than steers. The adapt option is off and the router follows only the grid. FPY feeds the /model-router view, the report, and, for each task class, a recommended cell: the one with the lowest cost per successful task among cells with at least three tasks, without ever dropping below the grid for review-debug and design-open. If a recommendation consistently diverges from the grid, you can choose to add an exception in ## Model routing.

From version 0.4 (planned), FPY will steer choices. With adapt enabled, the router balances exploitation (using what works) and exploration (trying promising alternatives) through Thompson sampling:

  • For each cell it maintains a range of plausible FPY values modeled with a Beta distribution: alpha grows with time-weighted successes, beta with time-weighted rework and failures.
  • At each launch it draws a plausible FPY from each candidate cell near the grid, divides the cell's cost by that value, and picks the one with the lowest cost per successful task.
  • Cells with plenty of data draw values close to their measured FPY (a proven choice keeps winning); cells with little data have wider draws and get tested occasionally, up to a cap of 10% of decisions per class (exploreCap).
  • Without prior data, the grid's choice starts ahead (alpha = 2, beta = 1, an expected FPY of two-thirds) compared to neighboring cells (1, 1): the grid wins until the numbers prove otherwise.
  • A new project inherits your user-level history with weight equal to five tasks (projectPriorStrength), then gradually relies on its own data.
  • Exploration never drops below the grid for review-debug and design-open, never violates values set in ## Model routing, and never touches risky launches.

Why it only measures first. Versions 0.2 and 0.3 only measure, so you can verify in /model-router that the signals truly reflect how you work before trusting automatic selection.

Now that you know how to interpret the numbers, here are the five steps to make them appear on your machine.

Making statistics appear

No special configuration is needed, but five conditions must be met in order:

  1. Install model-router and use Claude Code 2.1.329 or later with mods enabled. Only the mod records data: if /model-router is unknown, the mod is not loaded.
  2. Leave measure enabled (it is on by default).
  3. Work normally, letting subagents run. Only subagent launches become tasks. If you write a launch by hand, add the class tag: an untagged launch that does not go through the judge stays without a task class and is excluded from learning.
  4. Wait for the rework window to close (30 minutes after the subagent's report, or at the end of the session).
  5. Open /model-router or ask for the model-router report. On opening, the view runs compaction for up to 3 seconds; press r to refresh.

Once the first tasks have closed, you can inspect the data in the terminal or in the browser.

The usage view and the report

Checking metrics does not clutter the conversation or consume context: /model-router opens an interactive view similar to Claude Code settings, visible only to you and never read by the model. It includes four tabs, a time range (24h, 7d, 30d, all), and a scope (user or project).

CommandWhat it does
/model-routerOpens the usage view on Overview, last 7 days, user scope

/model-router on, offTurns routing on or off for the current session

The Overview tab opens with four summary tiles:

  • FPY: 🟢 from 85%, 🟡 from 70%, 🔴 below;
  • Cost per successful task: 🟢 cheaper or 🔴 more expensive than the previous window;
  • Rework: 🟢 up to 10%, 🟡 up to 25%, 🔴 above;
  • Routed launches: ↓ downgraded, ↑ upgraded, = kept.

If a tile is based on fewer than five tasks it shows ⚪ weak: too little data to draw conclusions.

Keyboard shortcuts active as soon as the view opens: Tab and Shift+Tab switch tabs, ↓ and ↑ cycle through the time window, d w m a select it directly, p toggles between user and project scope, o opens the report, r refreshes, Esc closes.

If you prefer a broader view, the report page presents the same numbers — computed with the same aggregation — accompanied by weekly trends and a card for each task class. It is saved to <config dir>/model-router/report.html and opened locally.

Install the plugin, verify that mods are enabled on Claude Code 2.1.329 or later, and start a session. Routing and measurement start out enabled. Check that /model-router responds: on a machine with no history yet, Overview will report that no subagents have run yet.

From there, work as usual: every subagent launch prints its 🔀 line, tagged launches become tasks, and numbers appear as rework windows close.

A single project or everything you do

Press p in the view to toggle between the two scopes:

  • User scope: aggregates your data across all projects, offers the broadest picture, and fills up first.
  • Project scope: isolates work in the current repository (identified by the git remote or root directory). Samples are smaller, but they tell you whether the grid fits this specific codebase.

If project scope looks empty, the data was recorded under a different directory or remote.

Two practical points remain before you begin: where your data lives and what the plugin's current limits are.

Privacy

The plugin sends nothing it measures off your machine. All files stay local inside model-router/, in the active config directory (CLAUDE_CONFIG_DIR, otherwise ~/.claude):

  • the event log (events.jsonl), which keeps the first 2,000 characters of the prompts you type;
  • the options used by compaction;
  • user-level and project-level aggregates;
  • the HTML report page.

Nothing is written inside repositories. The only external call — the judge call for each routed launch — goes to the model provider just like any other request in your session. To turn off recording, set measure: false; to clear history, delete <config dir>/model-router/.

Limits

Four limits of the current version to keep in mind:

  • Only launches made through the Agent tool are routed; internal plugin agents and workflow agents are measured, but not routed.
  • The router never picks fable and, up to version 0.3, does not enforce the grid's minimum for review-debug and design-open.
  • Costs are engine estimates; edits made outside the session's tools are not detected.
  • Up to version 0.3, data is only measured, not used to decide. Adaptive selection based on quality data is planned for 0.4.
