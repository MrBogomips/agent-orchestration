model-router

model-router picks a model and an effort level for every subagent, child session and workflow agent with one written grid, routes the subagent starts that still carry no model, and measures on your machine how well each choice worked. This page explains it for everyone first, then in full detail.

In plain words

Claude Code can hand a piece of work to a subagent: a helper that starts with a fresh context, does one task and reports back. Every subagent runs on a model, and models differ in price and in care. A small, fast model is cheap and fine for looking something up. A large model costs more and is the right choice for a review or a hard decision. The effort level says how long the model thinks before answering.

Left alone, an agent starts every helper on its own model and effort. That wastes money on simple lookups and, worse, sometimes gives a hard review to a model too small for it, so the work comes back and has to be redone.

model-router does three things. It gives the agent a short written rulebook, the grid, so it chooses on purpose and says why. It catches the helpers started without a choice and asks a fast judge to classify them. And it measures: for each kind of task and each model and effort, how often the work was right the first time, the first-pass yield, and what one good result really cost.

How it works

model-router has two layers, and the first works without the second.

  • The skill, model-router:choose-model. It loads whenever the agent is about to start a subagent, a child session or a workflow, and states the grid. The agent decides before the start, passes model and effort explicitly, tags the description with the task class and writes one line saying what it chose. This works with mods off.
  • The mod, model-router. At a subagent start that still carries no model, it asks the judge and sets the model and the effort. It draws under each Agent call the model and effort the subagent actually got, records every decision and outcome, and serves the /model-router command. It needs mods on and Claude Code 2.1.329 or later.

The start call itself is never changed. The model is set when the subagent starts and the effort on each of the subagent's model requests, so routing works in every permission mode, auto mode included. Of the built-in subagent types, only general-purpose and Explore are routed.

The grid: how a choice is made

The grid has one machine-readable home, grid.json. The skill states it in prose, the setup skill lists its values, and a test fails when the three drift apart. For every start, the first rule that gives a value wins:

  1. An explicit choice by you, in the conversation.
  2. The project's ## Model routing section, when it names the kind of work or the task class.
  3. An agent definition that fixes its own model keeps it; only an effort is passed.
  4. The grid.

Model tiers

Go down the table and stop at the first row that fits.

TierFits whenExamples
haikuSimple, repetitive work whose result is easy to check, with no judgment calls.List or summarize files; run a single command; rename a symbol
sonnetWhat done looks like fits in one sentence.A well-specified change across a few files; tests for existing code
fableLarge and open-ended work where judgment and accuracy really matter. Both must hold.A complex design; an architecture decision with long-lasting consequences
opusEverything else, and any time you hesitate between two tiers.A review; debugging when the cause is unknown; most coordination work

The tier names are aliases; which model sits behind each is configuration. By price, cheapest first: haiku < sonnet < opus < fable.

Effort

Ask in order and stop at the first yes:

  1. Is it a simple task or a quick exchange? → low
  2. Would an unnoticed mistake cost money, a client or a wrong decision? → high
  3. Is it long, hard and critical, and does it run unattended? All three. → xhigh
  4. None of the above. → medium

Never max.

Task classes

The class goes at the start of the subagent's description, [mr:read-search], or [mr:edit-specified!] when the start is risky. It is how the measurements know what kind of work a task was.

Rules around the grid

  • In doubt, go up. Work that gets too small a model costs more in rework than the saving.
  • Risk belongs to the act, not the topic. Changing production, moving money or altering data that cannot be restored is risky; writing or testing code about such things is not. A risky start gets at least high effort and the ! marker.
  • Sessions: choose at the start. A running session's model is never changed.
  • Escalate one step at a time. Retry with specific feedback; then raise the effort one level; then start one tier up with a handoff.
  • A coordinator's own model. A session that mostly delegates runs on opus at medium, unless its own design work is hard.
  • Inline or delegate; continue, do not restart. A small task whose files are already in context is done inline, and a follow-up goes to the subagent already started on the topic.

Before each start, the agent writes the choice as one line: 🔀, the model, an effort bar of four cells, the effort, and the reason in under twelve words.

🔀 opus ▰▰▰▱ high -> review with unknown cause, going up
🔀 haiku ▰▱▱▱ low -> mechanical rename, easy to check

With the mod on, the same line appears in colour under each Agent call, with what the subagent actually got and why: explicit, fixed, judge: <class>; lowered from opus (or raised from, kept), judge: risky work; raised from <tier>, or keep: <why>.

How the judge works

The judge is internal to the mod: you never call it, and it runs only for a subagent start that carries no model and is not kept for one of the reasons above.

What it receives

The subagent type, its short description, and the first 4,000 characters of its task. The task is wrapped as data, every closing tag inside it is escaped, and the judge is told not to follow instructions inside it.

Its prompt

The prompt is generated from grid.json: the tiers behind fast, balanced and deep, the four effort questions numbered 0 to 3, the six classes, and the rule that risk is about the act. Change the grid and the judge's prompt changes with it.

The call

One model call to the fast tier (the fastModel option, haiku by default), at low effort, capped at 300 output tokens, with a time limit of 8 seconds (timeoutMs). It goes through your session's own client, like any subagent, and is counted in the session's cost.

Its answer

One JSON object:

{ "tier": "fast | balanced | deep", "confidence": 0.0, "effort": 0, "effort_confidence": 0.0, "risky": 0.0, "class": "<class>" }

What the router does with it

RuleDefaultWhy
Lowering the model needs confidence ≥0.6being wrong means a task gets too little
Raising the model needs confidence ≥0.3being wrong only costs money
risky above, or a ! tag0.7forces the deep tier and at least high effort, skipping both bars
Missing confidence—never changes the model, in either direction

The comparison is with the parent session's model. The effort is set when its own confidence passes the bar: low needs the lowering bar, higher levels the raising bar. An effort the call already carries is kept, and max is never set. The judge's tiers stop at opus, so the router never picks fable.

When it fails

The router fails open. A judge error, a timeout or an unreadable answer leaves the start unchanged and is logged as error, except that a start tagged ! still goes to the deep tier. Every decision is logged with its action: downgrade, upgrade, keep, explicit, forced-risk or error.

Configuring it

A project's exceptions: the Model routing section

The grid is the same everywhere; what differs per project goes into a ## Model routing section of the project's AGENTS.md (or CLAUDE.md). Ask "set up model routing for this project", or name the exception directly, such as "always use opus for migrations". model-router:setup finds the instruction file, asks about defaults and exceptions, suggests some from the repository, shows the exact section and writes it only after your clear yes. It does not commit.

How the statistics are collected

Events

The mod appends records to events.jsonl under the config folder: each routing decision; each subagent spawn, with its type, name and short description; signals (the files the session and its subagents write, failed tool calls, the prompts you type, stops and resumes); each subagent's report with its tokens and estimated cost; and session-end. Nothing calls a model to measure.

Tasks and outcomes

Each subagent start is one task. Its outcome is fixed when its rework window closes: 30 minutes after the subagent's report, or the end of the session if sooner.

OutcomeWhen
successthe subagent reported and nothing in the window redid its work
reworkin the window, the main session or another agent wrote one of its files; or a similar start of the same class followed; or one of the next two prompts you typed named its files or its task
failureit failed, or was stopped by its parent and redone
cancelledno report (a task that never reports closes after 24 hours), or stopped

"Similar" means that the distinct words the two descriptions share are at least half of all their distinct words, ignoring common words and the class tag.

Cells, numbers and aging

Outcomes are kept in cells of class × tier × effort, for example edit-specified · sonnet · medium. Each cell gives:

  • First-pass yield (FPY): success ÷ (success + rework + failure), how often the work was right the first time (see First-pass yield);
  • rework rate: rework ÷ (success + rework + failure);
  • cost per task: the mean estimated cost, from the engine's own estimate;
  • cost per successful task: cost per task ÷ FPY. A cheap model that is often wrong can cost more per success than a dearer one.

The aggregates are aged with a 30-day half-life (halfLifeDays): work from a month ago weighs half as much as today's. They are kept at two levels: user, you across all projects, and project, identified by its git remote, else its root folder.

Cancelled tasks, risky tasks, tasks with no class, tasks on a model outside the four families and tasks with no known effort are recorded but not learned. Read-only classes and cells with fewer than five tasks are weak signals and are flagged. For each class, the recommended cell is the one with the lowest cost per successful task among cells with at least three tasks, never below the grid for review-debug and design-open. Up to release 0.3 this is information only: the router does not act on it.

Compaction

Compaction closes the tasks whose window ended, appends their outcomes and folds them into the aggregates. It runs at session start, when the usage view opens or refreshes, and before the report, and it is safe to repeat: a task is never counted twice.

First-pass yield: the number behind every choice

First-pass yield, FPY for short, is borrowed from manufacturing. On a production line it is the share of pieces that come off the line good the first time, with no rework and no scrap. A line with 95% FPY reworks or throws away one piece in twenty. Nobody counts a reworked piece as good: it was paid for twice.

model-router applies the same idea to work handed to a subagent. One subagent start is one piece. It is good the first time if nothing in the next half hour had to redo it.

How it is counted

For each cell (class × tier × effort, for example edit-specified · haiku · low):

FPY = success ÷ (success + rework + failure)

  • success counts for FPY; rework and failure count against it. The outcomes are fixed as described in How the statistics are collected.
  • cancelled tasks are left out of both sides: a task you stopped, or one that never reported, says nothing about whether the model was up to it.
  • The counts are aged before they are divided: with the 30-day half-life, a success from a month ago counts as half a success. FPY follows how the models behave on your work now, not how they behaved in the spring.

Why FPY, and not just the price

The price list says what one task costs. It does not say what one good task costs, because a task that comes back is paid for again: by the rerun, by the main session that fixes it, and by your time. FPY turns the price into the number that matters, the cost per successful task:

cost per successful task = cost per task ÷ FPY

An example with two cells for the same kind of work, twenty closed tasks each:

Cellsuccess / rework / failureFPYCost per taskCost per successful task
haiku · low5 / 12 / 325%$0.020$0.080
sonnet · low18 / 2 / 090%$0.050$0.056

Haiku costs less than half per task, yet each good result costs more on it, because three tasks in four come back. And the table still flatters it: the fifteen tasks that came back also cost the main session's time and yours, which no price list shows. The opposite happens too: for a plain lookup a small model is right nineteen times in twenty, and paying for a bigger one buys nothing.

Reading it

  • The Overview tile is 🟢 from 85%, 🟡 from 70%, 🔴 below. The bars per tier and effort use the same colours.
  • Rework rate is the other face of FPY: rework ÷ (success + rework + failure). The two add up to 100% minus the failure rate.
  • A cell with fewer than five tasks is a weak signal (⚪): 100% over two tasks is luck, not evidence.
  • For the read-only classes (read-search, read-analyze) FPY is flagged as weak too. A reader writes no files, so the strongest rework signal, someone writing the same files afterwards, never fires: a poor search tends to look like a success.
  • FPY measures choices on your work, with signals that can misfire: if you edit a file a subagent wrote for a reason that has nothing to do with its work, that task counts as rework. Over many tasks the noise evens out; over a few it does not, which is why small cells are weak.

How the router uses it

Today (releases 0.2 and 0.3) FPY informs, it does not steer. The adapt option is off and the router chooses from the grid alone. FPY feeds the tiles and bars of /model-router, the report and, for each class, a recommended cell: the one with the lowest cost per successful task among cells with at least three tasks, never below the grid for review-debug and design-open. When a recommendation keeps differing from the grid, you act on it: an exception in the project's ## Model routing section.

From release 0.4 (planned) FPY steers. With adapt on, the router keeps for each cell not a single FPY but a range of plausible values, as a Beta distribution: its alpha grows with the aged successes, its beta with the aged rework and failures. At each subagent start it draws one plausible FPY from each candidate cell near the grid's choice, divides the cell's cost by it, and picks the cell with the lowest cost per success. This is Thompson sampling:

  • A cell with plenty of data draws values close to its measured FPY, so a proven choice keeps winning.
  • A cell with little data draws values spread wide, so now and then it wins a draw and gets tried. That is exploration, and it stops by itself once the data is clear. It is capped at 10% of a class's decisions (exploreCap).
  • Before any data, the grid's choice starts with a head start (alpha = 2, beta = 1, an expected FPY of two in three) and its neighbours start even (1, 1): the grid wins until the data says otherwise.
  • A project starts from your user-level record, worth five tasks (projectPriorStrength); as its own tasks pile up, its own record decides.
  • Exploration never goes below the grid for review-debug and design-open, never below the project's ## Model routing defaults, and never touches risky starts, which are measured but not learned.

Why measure first. Releases 0.2 and 0.3 only measure, so you can check in /model-router that the signals make sense on your work before they drive any choice.

Making the statistics appear

  1. Turn mods on and use Claude Code 2.1.329 or later. If /model-router is an unknown command, the mod is not loaded.
  2. Leave measure on. It is on by default.
  3. Let subagents run. Only subagent starts are tasks. Tag your own starts when you write them by hand: an untagged start that the router does not judge has no class and is not learned.
  4. Wait for the rework window. A task counts 30 minutes after its report, or once its session has ended.
  5. Open /model-router, or ask for the model-router report. Opening the view runs compaction for at most 3 seconds; press r to refresh.

The usage view and the report

/model-router opens a dialog laid out like Claude Code's own Settings dialog, with four tabs, a window (24h, 7d, 30d, all) and a level (user or project). Its answers are for you only: the model does not read them.

CommandDoes

/model-router [overview|models|classes|decisions] [24h|7d|30d|all] [user|project]Opens it on that tab, window and level, in any order
/model-router on, offTurns routing on or off for this session

/model-router helpLists the arguments and the keys

Overview opens with four tiles: FPY (🟢 from 85%, 🟡 from 70%, 🔴 below), cost per success (🟢 cheaper or 🔴 dearer than the window before), rework (🟢 up to 10%, 🟡 up to 25%, 🔴 above) and routed starts (↓ downgrades, ↑ upgrades, = keeps). A tile over fewer than five tasks shows ⚪ weak: too few to read.

The keys work as soon as the view opens: Tab and Shift+Tab switch tab, ↓ and ↑ step the window, d w m a pick it directly, p switches level, o opens the report, r refreshes, Esc closes.

The report page shows the same numbers, computed by the same aggregation, with a weekly trend and one card per class. It is written to <config dir>/model-router/report.html and opened locally.

A real session

What follows is what you can expect once model-router is installed: the moment you activate it, the first day, the first week and the first month.

Activating it

Install the plugin, make sure mods are on and Claude Code is 2.1.329 or later, and start a session. There is nothing else to switch on: routing and measuring are on by default. Check that /model-router is a known command; on a machine with no data yet, Overview says that no subagent has run in this session.

Then work as usual. Each subagent start gets its 🔀 line; tagged starts become tasks; the numbers appear as rework windows close.

One project, or everything you do

Press p to switch between the two levels. The user level is your data across every project: the broadest picture, and the one that fills first. The project level is the work done in this repository only, identified by its git remote, else its root folder: smaller numbers, but they answer whether the grid fits this codebase. If the project level shows nothing, the data was recorded under another folder or remote.

Privacy

The plugin sends what it records nowhere. It all stays under the active config folder (CLAUDE_CONFIG_DIR, else ~/.claude) in model-router/: the event log, which keeps the first 2,000 characters of the prompts you type; the options compaction uses; the aggregates per user and per project; and the report page. Nothing is written inside a repository. The judge's one call per routed start goes to the model provider like any other request of your session. Turn recording off with measure: false; to reset the data, delete <config dir>/model-router/.

Limits

  • Only starts made through the Agent tool are routed; a plugin's own agents and workflow agents are measured, not routed.
  • The router never picks fable, and up to 0.3 it does not hold review-debug and design-open to the grid's floor.
  • Costs are the engine's estimates. Edits made outside the session's own tools are not seen.
  • Up to 0.3 the data is measured, not used. Adaptive selection from the quality data is planned for 0.4.
