Two plugins for Claude Code

Multiple sessions. Multiple repositories. The right model for every task.

Work in parallel across multiple repositories without file conflicts and without wasting tokens. session-hub pairs a master session with a child session for each repository — each isolated in its own scope — while you step into the session you know best. model-router assigns the right model and effort to every delegated task and measures on your machine whether the choice paid off on the first try.

The problem

Outgrowing a single session in a single repository?

01

One agent for all repositories

Each agent loads the instructions, skills, and definitions from the folder where it starts. If you work on backend, frontend, and documentation from a single session at the hub root, you lose each repository's specific rules.

02

Multiple agents, no boundaries

Multiple active sessions end up stepping on each other's toes in the same files. You need real technical boundaries, not just prompt recommendations: who can write where, who can talk to whom, and how to handle out-of-scope requests.

03

One model for everything

Without a shared rule, every agent launches all subagents with its own model. Trivial lookups run on the most expensive model, while delicate reviews end up on one that is too light and come back to be redone.

session-hub

You work in your session. The master coordinates the others in parallel.

You step directly into the session that concerns you — design, prototype, or code — while the master starts the other child sessions, collects their updates, and routes what none of them can handle alone.

  • Real write boundaries, not recommendations. A hook blocks any edit to files outside the child session's write root, after resolving symlinks and ... It fails closed and explains why.
  • Requests go up, never sideways. If a child session needs a change in another repository, it does not touch it: it sends an out-of-scope request to the master.
  • Messages, never authorizations. With mods enabled, any message received from another session — including the master — is marked as information, never as an order or an implicit permission.
  • Children record and live panel. The master keeps the children record outside the hub; the live panel shows each child's status, model, effort, and last message.

model-router

The right model for every task, measured in the field.

Stop picking model and effort by gut feel. A clear grid decides before each launch, and local measurement shows you what it really costs to get a valid result on the first try.

  • An essential grid. Four model tiers, four effort questions, six task classes. At every launch the agent states the model, effort, and reason for the choice.
  • A judge covers what is missing. If a built-in subagent launches without a model, a fast classifier evaluates the task and sets model and effort on the fly. It fails open, leaving the launch unchanged on error.
  • Measured, not estimated. First-pass yield (FPY), rework rate, and cost per successful task, broken down by task class, model, and effort.
  • Only on your machine. All data stays locally in the Claude Code configuration folder: nothing is written into your repositories.

Architecture

Two plugins, one contract.

You can install and use each plugin completely on its own. When they work together, session-hub relies on model-router to pick the model and effort for each child session, without duplicating rules or cluttering your repositories.

Quickstart

Up and running in three steps.

  1. 1

    Install

    Add the marketplace and install either plugin or both. All you need is node in your PATH.

    /plugin install session-hub@mrbogomips
  2. 2

    Configure the hub

    Open Claude Code at the root of the folder containing your repositories and ask it to set up session-hub.

    set up session-hub for this hub
  3. 3

    Launch and measure

    Start a child session in a repository, let the subagents work, and then open the usage view.

    /model-router
