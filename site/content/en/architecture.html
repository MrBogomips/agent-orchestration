Architecture

Here is how the two plugins are built as shipped — session-hub {{version:session-hub}} and model-router {{version:model-router}}: what components make them up, how they talk to each other, what files they store on disk, and how they behave when something goes wrong.

Two plugins, two problems

When you work across multiple repositories in Claude Code, you face two distinct needs: coordinating isolated sessions without letting them step on each other's toes, and picking the right model and effort for each delegated task without guesswork. To keep responsibilities cleanly separated, the system is split into two standalone plugins.

PluginIn one line
session-hubA master session in a repository hub spawns one child session per repository, assigns each a scope, routes requests, and maintains a children record.
model-routerA single grid picks the model and effort for every subagent, child session, or workflow agent; a mod routes model-less subagent launches and locally measures how well each choice performed.

Because they solve different problems, the two plugins are designed to stay independent while working together seamlessly when you install both.

Independence and shared contract

You can use either plugin on its own without installing the other: session-hub never requires model-router, and model-router knows nothing about hubs. At the few integration points, one skill references the other by its full name (<plugin>:<skill>) and checks at runtime whether it is present.

The grid lives in one place — model-router:choose-model — and session-hub keeps no copy of it. When session-hub:spawn needs to determine the model and effort for a child session, it applies the first rule that yields a value:

  1. What you asked for in the conversation.
  2. The Model and Effort keys configured in the hub, per repository or per type of work.
  3. model-router:choose-model, if installed, applied to the child's handoff.
  4. The master's own --model and --effort; the summary notes that the child inherits them.

To keep changes in one plugin from breaking the other, everything they may assume about each other is locked down in a shared contract in the repository's design docs. Any change goes into the contract first in its own pull request; only then do the plugins adapt to it. The contract defines:

  • the precedence order above;
  • the --model and --effort launch flags;
  • the fixed SESSION_HUB_* environment variable names;
  • the naming rules and paths where each plugin stores its state.

Every externally visible surface carries the name of the plugin that owns it, so you can always tell where a message or file comes from: the session-hub-scope-guard hook, the session-hub and model-router mods and commands, the [session-hub] prefix on block messages, the 🔀 indicator in router output, the SESSION_HUB_* variables, and the session-hub/ and model-router/ state directories.

To enforce checks only where needed — and leave your normal sessions outside the hub untouched — the plugins first have to know for sure what role the current session holds.

Roles

A security check cannot guess a session's role from conversation text. Every session is therefore explicitly classified as master, child session, or neither.

RoleHow a session gets itWhat the plugins do
ChildThe launch command sets SESSION_HUB_ROLE=child; spawn handles this.The scope guard checks every file edit; with mods enabled, the send guard, shell check, origin tagging, and scope line are added.
MasterNo variable needed: any session in the hub that runs dispatch or spawn. With mods enabled, also any session that invokes the registry script with a literal absolute path or whose directory already has child sessions in the record.Skills spawn child sessions and update the record; with mods enabled, the children panel and scope line are added.
NeitherEverything else.The scope guard exits immediately without reading input; the mod neither blocks nor tags anything.

Environment variables are parsed conservatively so a typo can never disable the guards:

  • SESSION_HUB_ROLE is read case-insensitively with leading and trailing whitespace trimmed.
  • Any value other than an empty string, none, master, or child causes every guard to block.
  • The other variables propagated to a child session are SESSION_HUB_MASTER, SESSION_HUB_SCOPE_ROOT, SESSION_HUB_HANDOFF, SESSION_HUB_REGISTRY, and SESSION_HUB_GUARDS.

With components and roles in place, let's trace what happens step by step from the moment you hand work to the master.

The spawn flow

When you ask the master to work on one or more repositories, launching a child session follows a strict eight-step sequence:

  1. You ask the master for work touching repositories; dispatch determines that a child session is needed.
  2. The master reconciles the children record against live session names: any session no longer live is marked lost.
  3. It verifies that no active duplicate exists, then picks the environment, name, worktree, write root, and scope.
  4. It resolves model and effort from your request or the hub keys; if neither specifies them, it consults model-router:choose-model (when installed); failing that as well, it inherits the master's model and effort.
  5. It writes the handoff outside the hub (to a file, or inline for the desktop app).
  6. It launches the child session with the propagated flags, the child-specific flags, and the SESSION_HUB_* variables; Claude Code starts in the repository and reads the handoff.
  7. It records the child session as running and shows you a summary for each child: repository, write root, model and effort, environment, and any warnings.
  8. From then on, every Edit, Write, and NotebookEdit call in the child passes through the scope guard.

The children record never blocks a launch: if registry.mjs returns an error, spawn warns you and starts the child session anyway.

The final step of the flow hands boundary enforcement over to an automated technical check: here is how the scope guard works in detail.

The scope guard

Instructions in the handoff tell a child session where it should work, but they do not physically prevent an out-of-bounds write. To turn scope into a hard boundary, the hook runs node "${CLAUDE_PLUGIN_ROOT}/hooks/scope-guard.mjs" before every Edit, Write, and NotebookEdit call, with a 10-second timeout. It runs in every session, but acts only in child sessions: it exits with code 0 to allow the call, or code 2 to block it and explain the reason to the model.

  • Real paths. Both the write root and the target are resolved component by component, following symbolic links: a symlink inside the root that points outside is blocked. A path counts as inside only if it matches the root or starts with the root followed by a path separator.
  • Absolute paths only. A relative target or one starting with ~ is blocked; setting / or the home directory as the write root is treated as a configuration error.
  • Fails closed. An unknown role, a missing or invalid root, unreadable input, a call with no path, an unresolvable path, or an internal error always blocks. If node itself fails to start, the shell wrapper in hooks.json checks the role and blocks unless the session is not a child session or guards are disabled.
  • Early self-timeout. Claude Code treats a timed-out hook as a non-blocking error; to make sure nothing slips through, the scope guard blocks on its own after 7 seconds.

The scope guard protects file-editing tools even without mods. When mods are enabled, session-hub extends coverage to cross-session messages, the shell, and the UI.

The session-hub mod

A child session could still try to write through the shell or contact a sibling session directly, while you in the master need to keep an eye on the sessions you launched. The session-hub mod handles all of this, loaded from the modules entry of the same hooks/hooks.json with its logic in plain .mjs modules.

The mod writes no files to disk: it reads the children record, keeps everything else in session memory, and rebuilds it when a session is resumed.

Both session-hub's skills and its mod read and update a single shared store: the children record.

The children record

To track child sessions without cluttering the hub or repositories — and avoid corruption when multiple commands access the same file — session-hub stores the record at <config dir>/session-hub/children-<hub id>.json.

The hub ID is the first 16 hex digits of the SHA-256 hash of the hub's real path normalized to Unicode NFC, so the same hub reached via a symlink gets the same ID. The directory is created with mode 0700, and the record file and its lock with mode 0600.

  • Commands: path, read, upsert, status, request, and reconcile, each with --hub or --file.
  • Locking: an exclusive <record>.lock file; writers wait up to 5 seconds, and a lock older than 30 seconds is treated as stale.
  • Atomic writes: write to a temporary file in the same directory, flush to disk, and rename over the record.
  • Never overwritten if unreadable: a file that does not contain valid JSON, or belongs to a newer format version, is reported and left untouched so you can inspect it.
  • Statuses: running → waiting-user, done, abandoned, or lost; reconcile marks an active entry missing from the session list as lost and rejects an empty list.

The record wraps up session-hub's side of the architecture. Now let's turn to model-router, starting with the file every decision stems from: the grid.

The grid and grid.json

Model selection rules are needed in three different places: the prose skills, the judge prompt, and the quality loop. Keeping them in sync by hand would be brittle, so grid.json serves as the machine-readable source for the whole plugin. It holds:

  • the tiers in check order and price order;
  • the effort values and their questions;
  • the six task classes with each class's usual pick;
  • the tag format and the judge mapping: fast = haiku, balanced = sonnet, deep = opus.

choose-model exposes the same grid in prose for the agent, while setup lists the values a project can configure. To keep the three files from drifting apart, grid.test.mjs fails as soon as they fall out of sync, so any change to the grid updates grid.json and both skills together.

At runtime, the router mod reads tiers, effort questions, and task classes from grid.json to build the judge prompt, while the quality loop uses each task class's usual pick as its prior.

Now let's see how the router mod applies this grid when a subagent starts and how it collects quality data.

The router mod

The model-router mod coordinates three jobs: routing launches without an explicit model, calling the judge to classify the work, and logging the events that feed the quality loop.

Routing

When a subagent starts via the Agent tool, the mod cannot simply rewrite the input in a single hook: in auto permission mode, Claude Code rejects a call whose input was modified by a hook after review. Instead, the work is split into three steps:

  1. A tool.call hook evaluates the case, calls the judge if needed, and forwards the call unchanged.
  2. The subsequent agent.spawn hook sets the model relative to the caller's model and logs the decision.
  3. A turn.step hook applies the chosen effort to each model request made by the subagent.

The judge

Classifying a task on the fly has to cost little, finish within seconds, and resist manipulation by the task text. The judge meets those constraints as follows:

  • Tight budget: a single call on the fast tier at low effort, capped at 300 tokens and within 8 seconds.
  • Safe prompt: generated from grid.json; the task text is truncated to 4,000 characters, wrapped as a data block, and has closing tags escaped.
  • Structured response: a JSON object with tier, confidence, effort, effort confidence, risk, and task class.
  • Conservative thresholds: stepping down a tier requires 0.6 confidence, while stepping up takes only 0.3; risk above 0.7, or a ! tag, forces the deep tier and at least high effort.

The quality loop

A routing choice should be judged by actual results, not just initial intuition. For that reason, the mod appends decision, spawn, signal, report, and session-end events to events.jsonl.

Compaction — run at session start, from the usage view, and from the report — turns those events into usable statistics:

  1. It determines the outcome of every task whose rework window has closed and appends it as an outcome entry.
  2. It folds outcomes into task class × tier × effort cells across two scopes (user and project), with time decay and the grid as prior.

The report page and the usage view share the same aggregation logic, lib/usage-data.mjs, so the numbers always match. Up through 0.3, the router only collects and displays this data without using it to change routing decisions.

Planned for 0.4 (still provisional): with adapt enabled, Thompson sampling across the grid pick and adjacent cells using the grid as prior; exploration capped at 10% of recent decisions for a task class and no exploration on risky launches; writing recommendations.json during compaction so choose-model can read it.

Understanding how the hooks work and where files live helps explain why the two plugins react in opposite ways when something goes wrong.

Failure behavior

Not all errors carry the same weight: violating a repository's scope can damage code, whereas skipping a model optimization at worst makes a call slower or more expensive. By design, the two plugins therefore fail in opposite directions.

session-hub

Fails closed

A guard that cannot evaluate a call in a child session blocks it and explains why. A corrupt record, a newer format version, or a lock that cannot be acquired stops the write and leaves the file as is. The record itself, however, never stops work: skills warn you and continue without recording.

model-router

Fails open

An error never stops work. A judge error, timeout, or unreadable response leaves the launch unchanged; every hook has a catch that lets the event proceed. If the recommendations file is missing, the grid alone decides. An interrupted compaction can be rerun safely.

The underlying logic is simple: a guard that accidentally lets a write through violates the scope it exists to defend, whereas a router that accidentally blocks a launch stops work it exists only to optimize.
