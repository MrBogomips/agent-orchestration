Architecture

How the two plugins are built, as released: session-hub {{version:session-hub}} and model-router {{version:model-router}}. What each is made of, how the parts work together, what they keep on disk, and how each behaves when something fails.

Two plugins, two problems

PluginIn one line
session-hubA master session in a hub of repositories starts one child session per repository, gives each a scope, routes their requests and keeps a record of them.
model-routerOne written grid decides the model and the effort of every subagent, child session or workflow agent; a mod routes subagent starts carrying no model and measures locally how well each choice worked.

Independence and the shared contract

Each plugin works without the other. session-hub never requires model-router, and model-router knows nothing about hubs. Where they meet, a skill names the other plugin's skill in full (<plugin>:<skill>) and checks at run time whether it is installed.

The grid has one home: model-router:choose-model. session-hub holds no copy of it. When session-hub:spawn chooses a child's model and effort, the first rule that gives a value wins:

  1. What the user said in the conversation.
  2. The hub's Model and Effort keys, per repository or per kind of work.
  3. model-router:choose-model, when installed, applied to the child's handoff.
  4. The master's own --model and --effort; the report says the child inherits.

What each plugin may assume about the other is written in a shared contract in the repository's design documents: the precedence above, the launch flags --model and --effort, the fixed names of the SESSION_HUB_* variables, the naming rules and where each plugin keeps its state. The contract changes first, in its own pull request, before either plugin builds on the change.

Everything visible outside a plugin carries its name: the session-hub-scope-guard hook, the session-hub and model-router mods and commands, the [session-hub] prefix of block messages, the 🔀 of what the router shows, the SESSION_HUB_* variables and the session-hub/ and model-router/ state folders.

Roles

A session is a master, a child or neither. No role is ever inferred from the conversation.

RoleHow a session gets itWhat the plugins do in it
ChildIts launch command sets SESSION_HUB_ROLE=child; spawn does this.The scope guard checks every edit; with mods on, the send guard, the shell check, origin marking and the scope line.
MasterNo variable needed: a session in the hub that runs dispatch or spawn. With mods on, also one that runs the record script with a literal absolute path, or whose folder's record already lists children.The skills start children and keep the record; with mods on, the children panel and the scope line.
NeitherAnything else.The guard exits at once without reading its input; the mod guards and marks nothing.

SESSION_HUB_ROLE is read without regard to case or surrounding spaces. Any value other than empty, none, master or child makes every guard block, so that a typo cannot switch the guards off. The other variables are SESSION_HUB_MASTER, SESSION_HUB_SCOPE_ROOT, SESSION_HUB_HANDOFF, SESSION_HUB_REGISTRY and SESSION_HUB_GUARDS.

The spawn flow

  1. The user asks the master for work that touches repositories; dispatch decides a child is needed.
  2. The master reconciles the record with the live session names: children no longer live are marked lost.
  3. It checks for a live duplicate, then picks the environment, the name, the worktree, the write root and the scope.
  4. It takes the model and effort from the user or the hub's keys; otherwise asks model-router:choose-model if installed; otherwise inherits the master's.
  5. It writes the handoff outside the hub (a file, or inline for the desktop app).
  6. It launches the child with the carried flags, the child flags and the SESSION_HUB_* variables; Claude Code starts in the repository and reads the handoff.
  7. It records the child as running and reports per child: repository, write root, model and effort, environment, caveats.
  8. From then on, every Edit, Write and NotebookEdit of the child goes through the scope guard.

The record never blocks a start: if registry.mjs reports an error, spawn tells the user and starts the child anyway. Out-of-scope requests flow back the other way, always through the master:

The scope guard

The hook runs node "${CLAUDE_PLUGIN_ROOT}/hooks/scope-guard.mjs" with a 10-second timeout before every Edit, Write and NotebookEdit, in every session, and acts only in a child. Exit status 0 allows the call; exit status 2 blocks it, and the reason is shown to the model.

  • Real paths. The root and the target are resolved part by part, following symbolic links, so a link inside the root that points outside is blocked. A path is inside when it equals the root or starts with the root followed by a separator.
  • Absolute paths only. A relative target or one starting with ~ is blocked; a root of / or the home folder is a configuration error.
  • Fails closed. Unknown role, missing or invalid root, unreadable input, a call with no path, an unresolvable path, an internal error: all block. If node itself cannot run, the shell wrapper in hooks.json checks the role and blocks unless the session is not a child or guards are off.
  • Ahead of the timeout. Claude Code treats a hook that exceeds its timeout as a non-blocking error, so the guard blocks on its own after 7 seconds.

The session-hub mod

The mod loads from the modules entry of the same hooks/hooks.json, with its logic in plain .mjs modules. It writes no file: it reads the record and keeps the rest in the session's memory, which is rebuilt after a resume.

The send guard and the shell check fail closed; the marking, the scope line and the panel only inform and never block. When an organization's managed mod runs first and skips an event, the mod falls back to sending the scope line as context.

The children record

<config dir>/session-hub/children-<hub id>.json, where the hub id is the first 16 hex digits of the SHA-256 of the hub's real path in Unicode NFC form, so the same hub reached through a link gets the same id. The folder is created with mode 0700, the file and its lock with 0600.

  • Commands: path, read, upsert, status, request and reconcile, each with --hub or --file.
  • Locking: an exclusive <record>.lock; a writer waits up to 5 seconds, and a lock older than 30 seconds is stale.
  • Atomic writes: a temporary file in the same folder, flushed, then renamed over the record.
  • Never overwritten when unreadable: a file that is not valid JSON, or from a newer format version, is reported and left for the user.
  • Statuses: running → waiting-user, done, abandoned or lost; reconcile marks as lost a live entry missing from the session list, and refuses an empty list.

The grid and grid.json

grid.json is the machine-readable source of the grid: tiers in check order, the price order, the effort levels and questions, the six classes with each one's usual choice, the tag format, and the judge mapping fast = haiku, balanced = sonnet, deep = opus.

choose-model states the same grid in prose for the agent, and setup lists the values a project may use. grid.test.mjs fails when the three drift apart, so a change to the grid touches grid.json and both skills in the same change. The router mod reads the tiers, effort questions and classes from grid.json to build the judge's prompt, and the quality loop reads each class's usual choice as its prior.

The router mod

Routing

Three hooks share the work at a subagent start through the Agent tool. A tool.call hook decides the case and asks the judge, and passes the call on unchanged: in auto permission mode the engine refuses a call whose input a hook changed after review. The agent.spawn hook that follows sets the model against the parent's model and logs the decision. A turn.step hook sets the routed effort on each of the subagent's model requests.

The judge

One call to the fast tier, at low effort, capped at 300 tokens, within 8 seconds. Its prompt is generated from grid.json; the task is cut at 4,000 characters, wrapped as data, with closing tags escaped. It answers one JSON object with a tier, a confidence, an effort, an effort confidence, a risk and a class. A downgrade needs confidence 0.6, an upgrade 0.3; risk above 0.7, or a ! tag, forces the deep tier and at least high effort.

The quality loop

The mod appends decision, spawn, signal, report and session-end records to events.jsonl. Compaction, started at session start, by the usage view and by the report, decides the outcome of every task whose rework window closed, appends it as an outcome record, and folds the learned ones into cells of class × tier × effort at two levels, user and project, with aging and the grid as prior. The report page and the usage view share one aggregation, lib/usage-data.mjs, so their numbers agree. Up to 0.3 the router does not use the data.

Planned for 0.4, and provisional: with adapt on, selection by Thompson sampling among the grid's choice and its neighbours, the grid as prior, exploration capped at 10% of a class's recent decisions, risky starts never explored, and recommendations.json written by compaction for choose-model to read.

Failure policy

The two plugins fail in opposite directions, on purpose.

session-hub

Fails closed

A guard that cannot evaluate a call in a child blocks it and says why. A corrupt record, a newer format or a lock that cannot be taken stops the write and leaves the file as it is. The record never stops the work, though: the skills tell you and carry on without recording.

model-router

Fails open

An error never stops work. A judge error, a timeout or an unreadable answer leaves the start unchanged; every hook has a catch that passes the event on. A missing hints file means the grid alone decides. A compaction that dies is safe to repeat.

The reasoning: a guard that lets a write through by mistake breaks the scope it exists to hold, while a router that blocks a start by mistake stops work it exists only to tune.
