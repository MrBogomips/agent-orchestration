Architecture

This page shows how the two released plugins (session-hub {{version:session-hub}} and model-router {{version:model-router}}) are built: what components make them up, how they talk to each other, what files they write to disk, and how they behave when something goes wrong.

Two plugins, two problems

Working across multiple repositories in Claude Code brings up two distinct needs: coordinating isolated sessions without letting them step on each other's toes, and picking the right model and effort for each delegated task without guessing. To keep responsibilities cleanly separated, the system is split into two standalone plugins.

PluginIn one line
session-hubA master session at the hub root spawns one child session per repository, assigns each a scope, routes requests, and keeps the child session record up to date.
model-routerA single grid picks the model and effort for every subagent, child session, or workflow agent; a mod routes model-less subagent launches and locally measures how each choice paid off.

Because they solve different problems, the two plugins are designed to stay independent while working seamlessly together when installed side by side.

Independence and shared contract

You can use either plugin on its own without installing the other: session-hub never requires model-router, and model-router knows nothing about hubs. At the few touchpoints between them, one skill invokes the other by its full name (<plugin>:<skill>) and checks at runtime whether it is installed.

The grid lives in one place — model-router:choose-model — and session-hub keeps no copy of it. When session-hub:spawn needs to pick the model and effort for a child session, it applies the first rule in priority order that returns a value:

  1. What you explicitly asked for in the conversation.
  2. The Model and Effort keys configured in the hub, per repository or per type of work.
  3. model-router:choose-model, if installed, applied to the child session's handoff.
  4. The master's own --model and --effort; the summary explicitly notes that the child session inherited them.

So a change in one plugin cannot break the other, everything they are allowed to assume about each other is locked down in a shared contract in the repository's design docs. Any change lands in the contract first via its own pull request; the plugins only adapt afterward. The contract defines:

  • the precedence order above;
  • the --model and --effort launch flags;
  • the fixed SESSION_HUB_* environment variable names;
  • the naming rules and paths where each plugin stores its state.

Every externally visible surface carries the name of the plugin that owns it, so you always know where a message or file came from: the session-hub-scope-guard hook, the session-hub and model-router mods and commands, the [session-hub] prefix on block messages, the 🔀 marker in router output, the SESSION_HUB_* variables, and the session-hub/ and model-router/ state directories.

In both plugins, the skills and the classic hook work even when mods are disabled. Mod-based features require mods to be enabled and Claude Code 2.1.329 or later.

To enforce checks only where needed — leaving your regular sessions outside the hub untouched — the plugins first have to know for sure what role the current session holds.

Roles

A security check cannot guess a session's role by reading the conversation. Every session is therefore explicitly classified as a child session, master, or neither.

RoleHow a session gets itWhat the plugins do
ChildThe launch command sets SESSION_HUB_ROLE=child (handled by spawn).The scope guard checks every file edit; with mods enabled, the send guard, shell check, origin tagging, and scope line also kick in.
MasterNo variable needed: any session in the hub running dispatch or spawn. With mods enabled, also any session that calls the record script with a literal absolute path or whose directory already has child sessions in the record.Skills launch child sessions and update the record; with mods enabled, the child session panel and scope line are added.
NeitherEvery other case.The scope guard exits immediately without reading input; the mod neither blocks nor tags anything.

Environment variables are parsed conservatively so a typo can never silently disable guards:

  • SESSION_HUB_ROLE is read case-insensitively with leading and trailing whitespace trimmed.
  • Any value other than an empty string, none, master, or child causes every guard to block.
  • The other variables passed to a child session are SESSION_HUB_MASTER, SESSION_HUB_MASTER_REF, SESSION_HUB_MASTER_SESSION_ID, SESSION_HUB_SCOPE_ROOT, SESSION_HUB_HANDOFF, SESSION_HUB_REGISTRY, and SESSION_HUB_GUARDS. Name, ref, and session ID identify the master: the name can change, the session ID cannot.

With components and roles in place, let's trace what happens step by step from the moment you hand a task to the master.

The spawn flow

When you ask the master to work on one or more repositories, launching a child session goes through eight ordered steps:

  1. You give the master work that touches repositories; dispatch determines that a child session is needed.
  2. The master reconciles the child session record against currently live session names, marking any session that is no longer running as lost.
  3. It checks that no live duplicate already exists, then resolves the environment, name, optional worktree, write root, and scope.
  4. It resolves model and effort from your request or the hub keys; if neither is set, it consults model-router:choose-model (if installed); if that isn't available either, it inherits the master's model and effort.
  5. It writes the handoff outside the hub (to a file, or inline for the desktop app).
  6. Launches the child session with the propagated flags, child-specific flags, and SESSION_HUB_* variables; Claude Code starts in the repository, and the handoff hook puts the handoff text into the child's context.
  7. It records the child session as running and shows you a summary per child: repository, write root, model and effort, environment, and any warnings.
  8. From that point on, every Edit, Write, and NotebookEdit call in the child session runs through the scope guard.

The child session record never blocks a launch: if registry.mjs returns an error, spawn warns you and starts the child session anyway.

Conversely, when a child session needs something outside its scope, the request travels back the other way — always through the master.

The final step of the spawn flow hands boundary enforcement over to an automated technical check. Here is how the scope guard works under the hood.

The scope guard

Handoff instructions tell a child session where it should work, but they don't physically stop a stray write. To turn scope into a hard boundary, the hook runs node "${CLAUDE_PLUGIN_ROOT}/hooks/scope-guard.mjs" before every Edit, Write, and NotebookEdit call with a 10-second timeout. It runs in every session, but only steps in inside child sessions: it exits with code 0 to allow the call, or code 2 to block it and explain why to the model.

  • Real paths. Both the write root and the target path are resolved component by component, following symlinks: a symlink inside the write root pointing outside it is blocked. A path counts as inside only if it equals the write root or starts with the write root followed by a path separator.
  • Absolute paths only. Relative targets or paths starting with ~ are blocked; setting / or the home directory as the write root is treated as a configuration error.
  • Fails closed. An unknown role, missing or invalid write root, unreadable input, missing path on the call, unresolvable path, or internal error always blocks. If node itself fails to start, the shell wrapper in hooks.json checks the role and blocks unless the session is not a child session or guards are disabled.
  • Pre-timeout cutoff. Claude Code treats a timed-out hook as a non-blocking error; to keep anything from slipping through, the scope guard self-blocks after 7 seconds.

The scope guard protects file-editing tools even without mods. When mods are enabled, session-hub extends coverage to cross-session messaging, the shell, and the UI.

The session-hub mod

A child session could still try to write files via the shell or message a sibling session directly, while you in the master need an easy way to keep an eye on running sessions. The session-hub mod handles all of this, loaded from the modules entry of the same hooks/hooks.json with its logic in plain .mjs modules.

The mod writes no files to disk: it reads the child session record, keeps everything else in session memory, and rebuilds it when a session is resumed.

Both the skills and the session-hub mod read and update a single shared store: the child session record.

The child session record

To track child sessions without dirtying the hub or repositories — and avoid corruption when multiple commands hit the same file — session-hub stores the record at:

<config dir>/session-hub/children-<hub id>.json

The <hub id> is the first 16 hex digits of the SHA-256 of the hub's real path normalized to Unicode NFC, so reaching the same hub via a symlink always yields the same ID. The directory is created with mode 0700, and the record file and its lock with 0600.

  • Commands: path, read, upsert, status, request, and reconcile, each taking --hub (plus --file for a record at an alternate path). An unrecognized option exits with an error without writing anything, and any path that resolves inside the hub — even through a symlink or a directory that does not exist yet — is rejected.
  • Locking: an exclusive <record>.lock file; writers wait up to 5 seconds, and any lock older than 30 seconds or owned by a dead process is treated as stale and taken over atomically so two processes cannot delete each other's lock.
  • Atomic writes: writes go to a temp file in the same directory, flush to disk, and rename over the record.
  • Never overwritten if unreadable: a file containing invalid JSON or a newer format version is reported and left untouched so you can inspect it.
  • Statuses: running → waiting-user, done, abandoned, or lost; reconcile marks any active entry missing from the session list as lost and refuses an empty list.

The record wraps up the session-hub side. Next is model-router, starting with the file every decision stems from: the grid.

The grid and grid.json

Model-selection rules are needed in three places: the prose skills, the judge prompt, and the quality loop. Keeping them in sync by hand would be brittle, so grid.json serves as the single machine-readable source for the whole plugin. It holds:

  • the tiers in check order and price order;
  • the effort levels and their guiding questions;
  • the six task classes and the usual choice for each;
  • the tag format and judge mapping (fast = haiku, balanced = sonnet, deep = opus).

choose-model presents the same grid in prose for the agent, while setup lists the values a project can configure. To keep the three files from drifting apart, grid.test.mjs fails as soon as they get out of sync — so any change to the grid updates grid.json and both skills together.

At runtime, the router mod reads tiers, effort questions, and task classes from grid.json to build the judge prompt, while the quality loop uses each task class's usual choice as its prior.

Now let's look at how the router mod applies this grid when a subagent starts, and how it collects quality data.

The router mod

The model-router mod handles three coordinated jobs: routing launches that omit an explicit model, calling the judge to classify the work, and logging the events that feed the quality loop.

Routing

When a subagent is launched via the Agent tool, the mod cannot simply rewrite the input in a single hook: under auto permission mode, Claude Code rejects a call whose input was mutated by a hook after review. Instead, the work is split across three steps:

  1. A tool.call hook evaluates the case, calls the judge if needed, and forwards the call untouched.
  2. The subsequent agent.spawn hook sets the model relative to the caller's model and logs the decision.
  3. A turn.step hook applies the chosen effort to each model request the subagent makes.

The judge

Classifying a task on the fly has to be cheap, finish in seconds, and resist prompt injection from the task text itself. The judge meets those constraints in four ways:

  • Tight budget: a single call on the fast tier at low effort, capped at 300 tokens and an 8-second timeout.
  • Safe prompt: generated from grid.json; the task text is truncated to 4,000 characters, wrapped as a data block, and stripped of raw closing tags via escaping.
  • Structured response: a JSON object with tier, confidence, effort, effort confidence, risk, and task class.
  • Conservative thresholds: stepping down a tier requires confidence ≥ 0.6, while stepping up only takes ≥ 0.3; risk above 0.7 or a ! tag forces the deep tier and at least high effort.

The quality loop

Routing choices should be judged by real outcomes, not just initial intuition. To make that possible, the mod appends decision, spawn, signal, report, and session-end events to events.jsonl.

Compaction — run at session start, by the usage view, and by the report — turns those raw events into usable stats:

  1. It resolves the outcome of every task whose rework window has closed and appends it as an outcome entry.
  2. It folds outcomes into task class × tier × effort cells across two scopes (user and project), with time decay and the grid as prior.

The report page and the usage view share the same aggregation logic (lib/usage-data.mjs), so their numbers always match. Through version 0.3, the router only collects and displays this data without using it to alter routing decisions.

Planned for a later release (still provisional): when adapt is enabled, Thompson sampling selects between the grid's pick and its neighboring cells, using the grid as a prior; exploration is capped at 10% of recent decisions for a task class, with no exploration on risky launches; recommendations.json is written during compaction for choose-model to read.

Knowing how the hooks work and where files live makes it clear why the two plugins take opposite stances when something fails.

Failure behavior

Not all failures carry the same weight: violating a repository's scope can damage code, whereas skipping a model optimization at worst makes a call slower or pricier. By design, the two plugins fail in opposite directions.

session-hub: fails closed

Any guard that cannot evaluate a call in a child session blocks it and explains why. A corrupt record, a newer format version, or an unacquired lock halts the write and leaves the file untouched. The record itself, however, never stops your work: skills warn you and carry on without recording.

model-router: fails open

An error never stops your work. A judge failure, timeout, or unreadable response leaves the launch untouched; every hook wraps its logic in a catch that lets the event proceed. If the recommendations file is missing, the grid decides on its own. An interrupted compaction is safe to rerun.

The underlying principle is straightforward: a guard that accidentally lets a write through violates the scope it exists to defend, whereas a router that accidentally blocks a launch halts work it exists only to optimize.
