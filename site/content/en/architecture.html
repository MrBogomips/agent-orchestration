Architecture

This page shows how the two plugins are built in the released version (session-hub {{version:session-hub}} and model-router {{version:model-router}}): what components they consist of, how they interact, what files they store on disk, and how they behave when something goes wrong.

Two plugins, two problems

When you work across multiple repositories in Claude Code, you face two distinct needs: coordinating multiple isolated sessions so they do not step on each other, and choosing the right model and effort for each delegated task without guessing. To keep responsibilities clearly separated, the system is split into two independent plugins.

PluginIn one line
session-hubA master session in the hub root starts one child session per repository, assigns each a scope, dispatches requests, and keeps the children record up to date.
model-routerA single grid decides the model and effort for every subagent, child session, or workflow agent; a mod routes subagent spawns without a model and measures locally how well each choice performed.

Because they solve different problems, the two plugins are designed to stay independent while working together smoothly when you install both.

Independence and shared contract

You can use either plugin on its own without installing the other: session-hub never requires model-router, and model-router knows nothing about the existence of a hub. At the few contact points, one skill calls the other by its full name (<plugin>:<skill>) and checks at runtime whether it is installed.

The grid lives in one place — model-router:choose-model — and session-hub keeps no copy of it. When session-hub:spawn needs to determine the model and effort for a child session, it applies the first rule in priority order that returns a value:

  1. What you explicitly specified in the conversation.
  2. The Model and Effort keys configured in the hub, per repository or per type of work.
  3. model-router:choose-model, if installed, applied to the child session's handoff.
  4. The master's own --model and --effort; the report explicitly notes that the child inherits them.

To prevent one plugin from breaking when the other changes, everything they may assume about each other is fixed in a shared contract in the repository's design documents. Every change goes through the contract first in a dedicated pull request; only after that do the plugins adapt. The contract defines:

  • the precedence order shown above;
  • the --model and --effort launch flags;
  • the fixed names of the SESSION_HUB_* environment variables;
  • the naming rules and the paths where each plugin stores its state.

Everything visible outside a plugin carries the name of the plugin that owns it, so you always know where a message or file comes from: the session-hub-scope-guard hook, the session-hub and model-router mods and commands, the [session-hub] prefix in block messages, the 🔀 indicator in router output, the SESSION_HUB_* variables, and the session-hub/ and model-router/ state directories.

In both plugins, the skills and the classic hook work even with mods disabled. The features introduced by the mods require mods to be enabled and Claude Code 2.1.329 or later.

To apply checks only where they are needed — leaving your normal sessions outside the hub untouched — the plugins first need to know with certainty what role the current session has.

Roles

A security check cannot guess a session's role by reading the conversation. Every session is therefore explicitly classified as a child session, a master, or neither.

RoleHow a session takes itWhat the plugins do
ChildThe launch command sets SESSION_HUB_ROLE=child (handled by spawn).The scope guard checks every file edit; with mods enabled, the send guard, shell check, origin tagging, and scope line are also added.
MasterNo variable is needed: it is a session in the hub running dispatch or spawn. With mods enabled, this also includes a session that invokes the registry script with a literal absolute path or whose directory already has child sessions in the record.The skills start child sessions and update the record; with mods enabled, the child sessions panel and scope line are also added.
NeitherAny other case.The scope guard exits immediately without reading input; the mod neither blocks nor tags anything.

Environment variables are read conservatively so a typo can never disable the checks:

  • SESSION_HUB_ROLE is read case-insensitively, ignoring leading or trailing whitespace.
  • Any value other than an empty string, none, master, or child triggers blocking on all guards.
  • The other variables propagated to the child session are SESSION_HUB_MASTER, SESSION_HUB_SCOPE_ROOT, SESSION_HUB_HANDOFF, SESSION_HUB_REGISTRY, and SESSION_HUB_GUARDS.

With components and roles in place, let's trace step by step what happens from the moment you give the master a task.

The spawn flow

When you ask the master to work on one or more repositories, starting a child session goes through eight ordered steps:

  1. You give the master a task that touches repositories; dispatch decides that a child session is needed.
  2. The master reconciles the children record against the names of currently active sessions: any that are no longer running are marked as lost.
  3. It checks that no active duplicate exists, then determines the environment, name, optional worktree, write root, and scope.
  4. It derives the model and effort from what you asked for or from the hub keys; if missing, it consults model-router:choose-model (if installed); if that is also missing, it inherits the master's model and effort.
  5. It writes the handoff outside the hub (to a file, or inline for the desktop app).
  6. It launches the child session with the propagated flags, child-specific flags, and SESSION_HUB_* variables; Claude Code starts in the repository and reads the handoff.
  7. It records the child session as running and shows you a summary for each one: repository, write root, model and effort, environment, and any warnings.
  8. From that point on, every Edit, Write, and NotebookEdit call from the child session goes through the scope guard.

The children record never blocks a launch: if registry.mjs returns an error, spawn warns you and starts the child session anyway.

When a child session needs something outside its own scope, the request travels in the opposite direction, always going through the master.

The final step of the flow hands boundary enforcement over to an automatic technical check: here is how the scope guard works in detail.

The scope guard

The instructions in the handoff tell the child session where it should work, but they do not physically prevent an out-of-bounds write. To turn scope into a real boundary, the hook runs node "${CLAUDE_PLUGIN_ROOT}/hooks/scope-guard.mjs" before every call to Edit, Write, and NotebookEdit, with a 10-second timeout. It runs in all sessions, but intervenes only in child sessions: it exits with code 0 to allow the call, or with code 2 to block it and explain why to the model.

  • Real paths. Both the write root and the target are resolved component by component following symlinks: a symlink inside the root that points outside is blocked. A path is considered inside only if it equals the root or starts with the root followed by a separator.
  • Absolute paths only. A relative target or one starting with ~ is blocked; setting / or the home directory as the write root is treated as a configuration error.
  • Fails closed. An unknown role, a missing or invalid root, unreadable input, a call without a path, an unresolvable path, or an internal error always causes a block. If node itself fails to start, the shell wrapper in hooks.json checks the role and blocks unless the session is not a child session or guards are disabled.
  • Pre-empting the timeout. Claude Code treats a hook that exceeds its timeout as a non-blocking error; so that nothing slips through, the scope guard blocks on its own after 7 seconds.

The scope guard protects file-editing tools even without mods. When mods are enabled, session-hub extends coverage to inter-session messages, the shell, and the UI.

The session-hub mod

A child session can still try to write through the shell or contact a sibling session directly, while in the master you need to keep an eye on the status of the sessions you started. The session-hub mod handles all of this, loaded from the modules entry of the same hooks/hooks.json with its logic in plain .mjs modules.

The mod writes no files to disk: it reads the children record, keeps the rest in session memory, and rebuilds it when the session is resumed.

The send guard and the shell check fail closed; origin tagging, the scope line, and the panel are informational only and never block. If an organization-managed mod runs first and skips an event, the mod falls back to sending the scope line as context.

Both the skills and the session-hub mod read and update a single shared store: the children record.

The children record

To track child sessions without cluttering the hub or the repositories — and to avoid corruption when multiple commands access the same file — session-hub stores the record at:

<config dir>/session-hub/children-<hub id>.json

The <hub id> identifier is the first 16 hexadecimal digits of the SHA-256 of the hub's real path normalized to Unicode NFC, so the same hub reached through a symlink always gets the same ID. The directory is created with 0700 permissions, and the record file and its lock with 0600.

  • Commands: path, read, upsert, status, request, and reconcile, each with --hub (and --file for a record at a different path). An option the command does not accept exits with an error without writing anything, and a path that resolves inside the hub, even through a link or a directory that has not been created yet, is rejected.
  • Lock: an exclusive <record>.lock file; writers wait up to 5 seconds, and a lock older than 30 seconds, or whose process has exited, is treated as stale and taken over atomically, so two processes cannot delete each other's lock.
  • Atomic writes: write to a temporary file in the same directory, flush to disk, and rename over the record.
  • Never overwritten when unreadable: a file that does not contain valid JSON, or that belongs to a newer format version, is reported and left untouched so you can inspect it.
  • States: running → waiting-user, done, abandoned, or lost; reconcile marks an active entry missing from the session list as lost and rejects an empty list.

The record closes out the session-hub side. Let's move on to model-router, starting from the file where all of its decisions originate: the grid.

The grid and grid.json

The model-selection rules are needed in three different places: the prose skills, the judge prompt, and the quality loop. Keeping them in sync by hand would be fragile, so grid.json serves as the machine-readable source for the entire plugin. It contains:

  • the tiers in check order and price order;
  • the effort values and their questions;
  • the six task classes with the usual choice for each;
  • the tag format and the judge mapping (fast = haiku, balanced = sonnet, deep = opus).

choose-model presents the same grid in prose for the agent, while setup lists the values a project can configure. To prevent the three files from drifting apart, grid.test.mjs fails as soon as they fall out of sync: every change to the grid therefore updates grid.json and both skills together.

At runtime, the router mod reads tiers, effort questions, and task classes from grid.json to build the judge prompt, while the quality loop uses the usual choice for each task class as its prior.

Now let's look at how the router mod applies this grid when a subagent starts and how it collects quality data.

The router mod

The model-router mod performs three coordinated jobs: it routes spawns that have no explicit model, calls the judge to classify the work, and records the events that feed the quality loop.

Routing

When a subagent starts via the Agent tool, the mod cannot simply rewrite the input in a single hook: in automatic permission mode, Claude Code rejects a call whose input was modified by a hook after review. For that reason, the work is split into three steps:

  1. A tool.call hook evaluates the case, calls the judge if needed, and forwards the call unchanged.
  2. The subsequent agent.spawn hook sets the model relative to the caller's model and records the decision.
  3. A turn.step hook applies the chosen effort to each model request made by the subagent.

The judge

Classifying a task on the fly must cost little, finish in a few seconds, and resist manipulation from the task text. The judge meets these constraints in four ways:

  • Tight budget: a single call on the fast tier, with low effort, capped at 300 tokens and within 8 seconds.
  • Safe prompt: generated from grid.json; the task text is truncated to 4,000 characters, wrapped as a data block, with closing tags escaped.
  • Structured response: a JSON object with tier, confidence, effort, effort confidence, risk, and task class.
  • Conservative thresholds: stepping down a tier requires confidence ≥ 0.6, while stepping up only needs ≥ 0.3; risk above 0.7, or a ! tag, forces the deep tier and at least high effort.

The quality loop

A routing choice should be judged by real results, not just initial intuition. To do this, the mod appends decision, spawn, signal, report, and session-end events to events.jsonl.

Compaction — run on session start, from the usage view, and by the report — turns these events into usable statistics:

  1. Determines the outcome of every task whose rework window has closed and appends it as an outcome entry.
  2. Folds outcomes into task class × tier × effort cells across two scopes (user and project), with time decay and the grid as the prior.

The report page and the usage view share the same aggregation logic (lib/usage-data.mjs), so the numbers always match. Through version 0.3, the router only collects and displays these data without using them to change decisions.

Planned for 0.4 (still tentative): with adapt enabled, selection via Thompson sampling between the grid's choice and adjacent cells, using the grid as the prior; exploration capped at 10% of recent decisions for a task class and no exploration on risky spawns; writing recommendations.json during compaction so choose-model can read it.

Knowing how the hooks work and where the files live helps explain why the two plugins react in opposite ways when something goes wrong.

Failure behavior

Not all errors carry the same weight: violating a repository's scope can damage code, whereas skipping a model optimization at worst makes a call slower or more expensive. By design, the two plugins therefore behave in opposite ways.

session-hub: fails closed

A guard that cannot evaluate a call in a child session blocks it and explains why. A corrupt record, a newer format, or a lock that cannot be acquired stops the write and leaves the file as it is. The record itself never stops work, however: the skills warn you and continue without recording.

model-router: fails open

An error never stops work. A judge failure, a timeout, or an unreadable response leaves the spawn unchanged; every hook has a catch that lets the event proceed. If the recommendations file is missing, the grid alone decides. An interrupted compaction can be safely repeated.

The underlying logic is simple: a guard that accidentally lets a write through breaks the scope it exists to defend, whereas a router that accidentally blocks a spawn stops work it only exists to optimize.
