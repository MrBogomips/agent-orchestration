Quickstart

From nothing to a hub with two children working in parallel, and your first routing decisions on screen. Each step says what you should see, so you know it worked before you move on.

Requirements

RequirementValue
Claude Code, for the mods2.1.329 or later; both plugins declare engines["claude-code"]: ">=2.1.329" and were tested on 2.1.329 and 2.1.330
Claude Code, for messages between sessions (session-hub)2.1.224 or later
ModsTurned on, for the session-hub mod (send guard, shell check, origin marking, scope line, children panel, /session-hub) and the model-router mod (routing, measurement, the 🔀 line under Agent calls, /model-router)

The skills and the scope guard hook work with mods turned off. You lose the guards on messages and shell commands, the panel, the routing of subagent starts, the measurements and both commands.

Install from the marketplace

Both plugins are listed in the mrbogomips marketplace. Inside Claude Code:

/plugin marketplace add MrBogomips/claude-plugins
/plugin install session-hub@mrbogomips
/plugin install model-router@mrbogomips

Or from a shell:

claude plugin marketplace add MrBogomips/claude-plugins
claude plugin install session-hub@mrbogomips
claude plugin install model-router@mrbogomips

Each plugin works without the other. Installed together, session-hub:spawn loads model-router:choose-model to choose each child's model and effort; without model-router, a child inherits the master's model and effort, and spawn says so in its report.

Check that the mods are on

Type /session-hub or /model-router. If Claude Code does not know the command, the mod is not loaded: mods are off, or Claude Code is older than 2.1.329 (check with claude --version). In a session with no hub role, /session-hub answers:

session-hub: This session has no session-hub role. It becomes a master when it uses session-hub:spawn or session-hub:dispatch.

Set up a hub

A hub is any folder that holds several git repositories, as subfolders or submodules. Open Claude Code at its root and ask in plain words:

set up session-hub for this hub

session-hub:setup looks at the hub (child folders with .git, .gitmodules, each repository's base branch, worktree rules), proposes a ## Child sessions section for the hub's AGENTS.md (or CLAUDE.md), shows it, and writes it only after your explicit yes. It does not commit. Every key is optional: without the section, spawn uses the defaults and offers setup in its report.

Keep test hubs under your home folder. A hub under the system temporary folder loaded no project instruction file at all in testing.

Your first spawn

Run the master inside Herdr or tmux if you can: spawn then opens each child in a pane beside you, with the scope guard active. Ask for a task that touches two repositories:

T-42: add GET /export to product (CSV, at most 10 000 rows) and document the limit in design/docs/api/export.md.

dispatch loads, states its decision in a short table (one editing child for product, one for design), then calls spawn once for both, so each handoff names the other as a sibling. The report lists each child's name, repository, write root, model and effort, environment, how to open it, and any caveats.

First run in a repository. Folder trust is not inherited by a repository nested in a trusted hub. A child may stop at the trust prompt in its own pane, and claude --bg fails with Workspace not trusted. Answer the prompt (or open the repository once with claude), then let the master retry.

See your children: /session-hub

In the master, /session-hub shows the record's path and a table of the children: status in the record, live status from the session list, model and effort, last message. It also opens the children panel beside the chat, refreshed every 30 seconds. In a child, the same command shows its role, write root, handoff and whether the guards are on.

Your first routing decision

With model-router installed, choose-model loads whenever the agent is about to start a subagent. Ask for something that needs one, for example a search across a large repository. Before the start, the agent writes one line:

🔀 haiku ▰▱▱▱ low -> find callers of parseConfig, easy to check

The line reads: the model, an effort bar of four cells (one for low to four for xhigh), the effort, and the reason in under twelve words. With the mod on, the same line is drawn in colour under the Agent call's row, with the model and effort the subagent actually got after routing:

⏺ Agent([mr:read-search] Find the CSV writer)
  ⎿  🔀 haiku  ▰▱▱▱ low    -> judge: read-search; lowered from sonnet

Several Agent calls made in one message are drawn as one "background agents launched" row; press ctrl+o to see each call with its line.

See the measurements: /model-router

/model-router opens the usage view on Overview, last 7 days, user level. Tab and Shift+Tab switch between Overview, Models, Classes and Decisions; d, w, m, a pick the window; p switches between your data across projects and this project's; o writes and opens the report page; Esc closes.

Do not expect numbers at once. A task counts only once its rework window has closed, 30 minutes after the subagent's report or at the end of the session. What to expect after one day, a week and a month is shown in a real session.

Record a project's exceptions: model-router:setup

In a project where some work needs more than the grid gives, or can take less, ask:

set up model routing for this project

model-router:setup asks about defaults and exceptions, suggests some from the repository (migrations, infrastructure, billing, generated code, bulk refactors), shows the exact ## Model routing section and writes it to the project's AGENTS.md only after your clear yes. Details are on the model-router page.
