Concept

Two separate problems show up once a team works with Claude Code across several repositories: sessions that need limits, and agents that need the right model. session-hub answers the first, model-router the second. This page explains the ideas behind both before any command.

The problem

An agent loads the instructions, skills and agents of the folder it runs in. A product that spans a backend, a frontend, a design repository and the docs therefore needs a session started in each repository: a single session at the root, a subagent, or --add-dir all run from the wrong folder and miss the repository's own rules.

Once several such sessions run at the same time, they need limits. What may each one change? Whom does it talk to? Where does a request outside its task go? Which model does it spend? Without answers, parallel sessions step on each other's files and pass requests sideways that nobody approved.

Inside each session there is a second, quieter cost. An agent left to itself starts every subagent on its own model and effort. A file search runs on the most expensive model; a hard review sometimes runs on a cheap one and comes back for rework. Nobody sees which choice worked, because nothing measures it.

Hub, master and children

session-hub turns a folder of repositories into a hub. The session you open at the hub's root is the master. It coordinates, and it never writes in a child repository. For work in a repository, the master starts a child: a full Claude Code session whose working folder is that repository (or a worktree of it), so it loads that repository's rules.

Children run in parallel. That is the point: you can work directly in the child whose work you know, steering it as you would any session, while the master keeps the other children going and routes what passes between them. Ways of working shows this for one person and for a team.

Scope and the write root

Every child gets a written scope at launch, in its handoff: its goal, what it may change, what it may only read, its siblings, and the rules for messages. The one folder where a child may create and change files is its write root: its repository, or a worktree in a sibling folder made by the master.

The write root is not only a rule in the handoff. A hook, the scope guard, checks every file edit a child makes, resolves its real path through links and .., and blocks a write outside the root. When it cannot decide, it blocks and says why: it fails closed. A child that needs a change elsewhere sends an out-of-scope message to the master instead.

Messages are information, not authorization

Children talk to the master only, and every message starts with a fixed prefix, [<task> <repo>] <type>: <text>, where the type is question, out-of-scope, pr, done or abandoned. The master's messages start with [master].

A message between sessions carries information. It never carries authority: no session merges, pushes, deletes or changes settings because another session asked. Approval comes from a person, in their own session. With mods on, the session-hub mod enforces the master-only channel and puts a line in front of every message from another session that says it is information, not authorization.

Routing per task

model-router gives the agent one short grid to choose a model and an effort for each piece of work it delegates. Four model tiers, checked in order: haiku for simple work that is easy to check, sonnet when what done looks like fits in one sentence, fable for large and open-ended work where judgment really matters, and opus for everything else, and whenever you hesitate. Four questions pick the effort, from low to xhigh. Six task classes name the kind of work.

The agent writes one line for every start, so you see the choice the moment it is made:

🔀 opus ▰▰▰▱ high -> review with unknown cause, going up
🔀 haiku ▰▱▱▱ low -> mechanical rename, easy to check

When a built-in subagent start still carries no model, a fast judge model classifies the task and sets one. If anything goes wrong, the start goes ahead unchanged: the router fails open. The two plugins fail in opposite directions on purpose: a guard that lets a write through is worse than one that blocks, while a router that blocks work is worse than one that leaves it alone.

Measurement

A grid is a guess until it is checked against real work. model-router counts each subagent start as one task and decides its outcome once a rework window has closed: right the first time, redone, failed or cancelled. From those outcomes it keeps, for each task class, model tier and effort, the first-pass yield (how often the work was right the first time), the rework rate and the cost per successful task, which counts the price of rework too.

The numbers are kept for you across all projects and for each project, aged so that old work weighs less, and they stay under your Claude Code config folder. Up to release 0.3 the router only measures; choosing from the data is planned for 0.4.

Glossary

TermMeaning
HubA folder that holds several git repositories, each with its own instructions, skills and agents.
MasterThe session opened in the hub. It coordinates and never writes in a child repository.
ChildA Claude Code session started by the master in a repository (or a worktree of it), so that it loads that repository's rules.
Write rootThe one folder where a child may create and change files.
HandoffWhat the master writes for each child: role, goal, scope, references, siblings, message rules, first step.
Children recordA JSON file, kept by the master outside the hub, with one entry per child.
Scope guardThe hook that blocks a child's file edits outside its write root, and blocks when it cannot decide.
ModA module a plugin loads into Claude Code to change its interface or behaviour: a panel, a command, a hook on a tool call. Needs mods turned on.
GridThe rules model-router uses to choose a model tier and an effort level.
Task classOne of six fixed labels for the kind of work, such as read-search or review-debug.
JudgeOne call to a fast model that classifies a subagent start carrying no model and proposes a tier, an effort and a class.
First-pass yield (FPY)The share of tasks that were right the first time.
Rework windowThe time after a subagent's report (30 minutes by default, or the end of the session) during which a redo still counts against it.
