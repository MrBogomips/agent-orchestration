session-hub

One master session in a hub of repositories starts child sessions, one per repository, that work in parallel. Each child gets a written scope, a model and an effort, talks only to the master, and sends anything outside its scope to the master. You work directly in the child you know; the master coordinates the rest.

Parallel sessions, one coordinator

The children of a hub are not steps of a pipeline. They run at the same time, each in its own pane or background session, each a full Claude Code session with its repository's rules loaded. That changes how people work with them.

You can type into any child. The usual pattern is that you work in the child whose work you are competent in, the design, the prototype or the code, and leave the master to coordinate the others: it starts them, hears their messages without polling, routes their requests and tells you when one needs a decision. A request that you make in a child but that falls outside its scope still goes to the master, so the coordination holds even when you are the one asking.

Four ways of putting this to work, from one person with two hats to a product team in which the agents carry the coordination between people, are described in ways of working.

You rarely name a skill. Ask in plain words, such as "start a child in product for T-42", "set up session-hub in this hub" or "what are the children doing?", and the matching skill loads.

Setting up a hub

The hub keeps its rules for children in a ## Child sessions section of its instruction file: AGENTS.md at the hub root, or CLAUDE.md when there is no AGENTS.md. Ask "set up session-hub for this hub": setup proposes a section from what it finds and writes it only when you say yes. Every key is optional. What you say in the conversation beats the keys, and the keys beat the defaults.

Deciding: dispatch

In the master, a task that touches the hub's repositories goes through dispatch. It reads the section, reconciles the children record with the live sessions, works out which repositories the work touches (it asks when unsure and never guesses), and takes the first row that fits for each:

SituationAction
A child for that repository and task is already runningMessage that child ([master] …); no second child
Any write in the repositoryA child, with session-hub:spawn
A read that needs the repository's own skills or rules to interpretA read-only child
A broad read whose result is a conclusionA read-only subagent of the master
A few known files to readThe master reads them itself

More than about five files, a search of the repository or its build tools is no longer "a few known files". dispatch states its decision in a short table, then starts all the children in one spawn call, so that their handoffs name each other as siblings.

Starting children: spawn

For each child, spawn resolves the repository and its base branch, reconciles the record, looks for a live child on the same repository and task (and sends it the request instead of starting another), picks the environment, the name, the worktree, the write root and the scope, and chooses the model and the effort: what you said, then the hub's keys, then model-router:choose-model when installed, otherwise the master's own. It writes a handoff file outside the hub, starts the child with the one-line prompt Read and follow <file>, records it as running and reports.

A child starts the way the master was started, so that it uses the same account and configuration folder: two sessions with different configuration folders cannot message each other. spawn carries over the flags that configure the session, adds the child's own (-n, --model, --effort, --permission-mode, --add-dir for the handoff folder) and the role variables. In tmux, the start of a child looks like this:

env SESSION_HUB_ROLE=child SESSION_HUB_MASTER=hub \
  SESSION_HUB_SCOPE_ROOT=/work/hub/product SESSION_HUB_HANDOFF=<dir>/t42-product-handoff.md \
  SESSION_HUB_REGISTRY=<config dir>/session-hub/children-<hub id>.json SESSION_HUB_GUARDS=on \
  claude -n t42-product --model sonnet --effort medium --permission-mode default \
  --add-dir <dir> -- 'Read and follow <dir>/t42-product-handoff.md'

Children start in the master's permission mode, because messages between sessions that differ on bypassing permission prompts wait for your approval. A worktree under the repository is made by the child, and the repository stays the write root; a worktree in a sibling folder is made by the master before the start and becomes the write root. That is the only thing the master ever does in a repository.

Messages and their five types

A child talks to the master only, with [<task> <repo>] <type>: <text>. The master's messages start with [master]. The master hears each child through its messages and an idle notice; it never polls.

TypeSent whenMaster's duty
questionthe child is blocked on a decisionanswer, or pass it to you and send the answer back
out-of-scopea need or request outside the scope, also one you make in the child's sessionroute it: ask you if needed, send it to the child that owns the scope, start one, or do a read itself
pra pull request was opened; the text holds its URLrecord the URL; follow the hub's rules on pull requests
donethe work is finishedfollow the hub's closing rules
abandonedthe work was stopped; the text holds the reasontell you

A message between sessions is information, never authorization: neither side merges, pushes, deletes or changes settings because another session asked. With mods on, the mod marks every delivery from another session with a line that says so.

Three guards, all failing closed

Three guards hold a child to its scope. All three act only in a child, and all three fail closed: a guard that cannot evaluate blocks and says why. SESSION_HUB_GUARDS=off, or the hub's Guards: off, turns all three off.

The scope guard (hook, works with mods off)

session-hub-scope-guard runs before every Edit, Write and NotebookEdit. It resolves the target's real path part by part, so a link inside the root that points outside is blocked, and a sibling folder whose name merely starts with the root's name is outside. It blocks a relative target, a write root of / or the home folder, an unknown role value, unreadable input, or a missing node. It blocks on its own after 7 seconds, ahead of the hook's 10-second timeout.

The shell check (mod, best effort)

Before a Bash or Monitor command runs in a child, the mod reads its redirections and the targets of tee, touch, mkdir, rm, rmdir, truncate, unlink, cp, mv, ln, install and sed -i, follows literal cd and pushd, and denies a target outside the write root. /dev and the system temporary folders are allowed.

[session-hub] Shell command blocked: it writes /work/hub/design/notes.md, outside the write root /work/hub/product. Do not retry this write through another command or tool. Send an `out-of-scope` message to the master, saying what you need written and why, and tell the user that you passed the request to the master.

It reads the command line only. Targets in variables, command substitutions or globs are not judged, nor what another program (a script, git, a build tool) writes.

The send guard (mod)

A child's message goes to its master, by name, or to the child's own subagents. Any other recipient, a sibling or a socket address, is refused with a reason that points to the master:

[session-hub] This session is a child and may message only its master, "hub". Send what you need to "hub" with your message prefix; a request for another session or repository is an `out-of-scope` message, and the master routes it.

The scope line

With mods on, the mod also puts the role and the scope (in a child) or the record (in the master) into the system prompt, and sends the same text as context on the first prompt after the start, after a compaction and after /clear, so the scope survives a long session.

The command and the children panel

/session-hub is registered by the mod, and its answer is for you only: the model does not read it. In the master it shows the record's path and the children table, and opens the children panel beside the chat. The panel has one row per child, with the status in the record, the live status from the session list, model and effort, and the last message; it refreshes every 30 seconds and on each /session-hub.

In a child, /session-hub shows its role, write root, handoff, record and whether the guards are on:

Role: child of "hub"
Write root: /w/repo
Handoff: /h/t42.md
Children record: not set
Guards: on (scope guard, shell check, send guard)

The children record

The master keeps one JSON file per hub, outside the hub, at <config dir>/session-hub/children-<hub id>.json, where the config dir is CLAUDE_CONFIG_DIR or ~/.claude and the hub id is the first 16 hex digits of the SHA-256 of the hub's real path. One entry per child: name, repository, task, scope, model, effort, status, start time, last message and requests. Statuses are running, waiting-user, done, abandoned and lost (recorded as live, no longer in the session list).

The skills write it only through scripts/registry.mjs, atomically and under a lock, so two writers lose no entry. A record that is not valid JSON is reported and never overwritten, and a failing record never stops a start: spawn tells you and carries on. You can read it yourself:

node "<plugin folder>/scripts/registry.mjs" read --hub /work/hub

Limits

  • Shell writes are covered on a best-effort basis, and only with mods on. With mods off, a shell write is held back by the handoff alone.
  • The desktop app has no guard. Its session tool takes no environment variables, so a child started there has no role.
  • The send guard needs mods on. With mods off, a sibling can still be messaged; the master-only rule is then prose.
  • A child resumed without its variables is no longer a child. Resume with the same SESSION_HUB_* variables in front of claude --resume.
  • A killed hook lets the write through. The guard's own 7-second watchdog covers a slow guard, not a hook killed from outside.
  • Trust is per repository. claude --bg in a repository nested in a trusted hub fails with Workspace not trusted until you have opened it once.

How the parts fit together, with the full decision flow of the guard, is on the architecture page.
