session-hub

When a task spans multiple repositories, trying to manage everything in a single session makes it easy to lose the thread and blur boundaries. With session-hub, a master session opened at the hub root launches one or more child sessions—one per repository—that run in parallel.

Each child session gets a written scope, a model, and an effort level; it communicates only with the master and forwards anything outside its perimeter back up. That lets you step straight into the child session for your own domain and steer it closely, while the master coordinates everything else.

1. Parallel sessions, one coordinator

Working across multiple repositories in a single chat forces you either to go one step at a time or to jump constantly between disconnected windows. session-hub flips that model: child sessions aren't mere stages in a pipeline, they are full Claude Code sessions running in parallel—each in its own pane or in the background—with their repository's instructions, skills, and conventions already loaded.

This setup changes how you work in practice:

  • Step in where your judgment matters: you can jump into and type in any child session, typically the one for the repository you know best (design, prototype, or code).
  • The master orchestrates the rest without noise: it launches the other child sessions, receives their updates without constant polling, routes cross-project requests, and pulls you in when a human decision is needed.
  • Boundaries always hold: even if you directly ask a child session for something that belongs to another repository, the request still goes up to the master instead of crossing boundaries.

On the Ways of working page, you'll find four progressive examples of how to apply this pattern, from a solo contributor wearing two hats to a full AI-mediated product team:

  • 01 · Wearing two hats — Analyst and UI/UX designer in the same person.
  • 02 · Three hats, three repositories — Developer, analyst, and designer across product, design, and prototype.
  • 03 · AI pair programming, evolved — Two builder-agent pairs with a master agent between them.
  • 04 · The AI-mediated product team — A Product Manager in the master, a runnable prototype instead of mock-ups.

2. What's in the plugin

To orchestrate child sessions and enforce their boundaries automatically, session-hub combines three skills, a hook, a script, a mod, and a dedicated command:

NameTypeWhat it does
session-hub:dispatchskillRuns on the master side. For each repository, decides whether the master reads directly, delegates to a subagent, or needs a child session; handles incoming messages, routes out-of-scope requests, and keeps tasks reserved for the master.
session-hub:spawnskillLaunches one child session per repository (desktop app, Herdr, tmux, claude --bg, or manual commands) with scope, model, effort, SESSION_HUB_* role variables, and a handoff file, then records it in the children record.
session-hub:setupskillCreates or updates the ## Child sessions section in the hub's instructions file, writing it only after your explicit confirmation.
session-hub-scope-guardhookPreToolUse hook on Edit, Write, and NotebookEdit. In a child session, blocks any edit whose real path resolves outside the write root.
scripts/registry.mjsscriptReads and updates the children record atomically and safely.
session-hubmodIn a child session, enables the send guard, shell check, message-origin marking, and scope line. In the master, adds the child sessions panel. Requires active mods.
/session-hubcommandShows the current session's role and scope; in the master, also summarizes child sessions and opens the panel. Registered by the mod.

In day-to-day use, you almost never need to invoke a skill by name. Plain language is enough—for example, "start a child session in product for T-42", "configure session-hub in this hub", or "what are the child sessions doing?"—and Claude Code automatically loads the right skill.

The first step in getting the master to work effectively is describing how your hub is laid out.

3. Configuring a hub

To distribute work sensibly, the master needs to know which repositories make up the hub, what each one does, and how you prefer to launch sessions. All of this lives in the ## Child sessions section of the hub's instructions file: AGENTS.md in the root directory, or CLAUDE.md if AGENTS.md is not present.

You don't need to write this section by hand. Just ask "configure session-hub for this hub": the setup skill inspects the directory, drafts a proposal, and writes it only after you confirm.

Every key is optional and follows a clear precedence order: what you specify in conversation overrides keys in the file, which in turn override the defaults.

With a clear map of the hub in place, the master is ready to decide how to route each incoming task.

4. Deciding who does what: dispatch

Not every operation on a repository warrants spinning up a dedicated child session: the master alone can check a couple of files, whereas writing code or interpreting local conventions calls for the project's full environment. On the master, the dispatch skill makes that call.

When given a task involving hub repositories, dispatch reads the configuration, reconciles the record against currently active sessions, and identifies which repositories are involved (asking you to confirm if anything is unclear, never guessing). For each repository, it applies the first matching rule:

SituationAction
A child session is already running for that repository and taskSends a message to that child session ([master] …); does not start a second one
Any edit is needed in the repositoryStarts a child session with session-hub:spawn
A read requires the repository's skills or rules to interpretStarts a read-only child session
A broad read is needed whose output is a summary or conclusionDelegates to a read-only subagent of the master
Only a few known files need to be readThe master reads them directly

Beyond roughly five files—or whenever you need to search the repository or run its build tools—the work no longer counts as "a few known files." Before acting, dispatch shows you the plan in a compact table and then launches all required child sessions in a single call to spawn, so each handoff immediately lists the others as sibling sessions.

5. Launching child sessions: spawn

Once it knows which child sessions are needed, spawn prepares the environment, defines the scope, and launches them in five ordered steps:

  1. Resolves the repository and its base branch, then reconciles the children record.
  2. Checks whether an active child session already exists for that repository and task; if so, forwards the request to it instead of opening a duplicate.
  3. Determines the execution environment, session name, worktree (if any), write root, and read scope.
  4. Selects the model and effort following a strict priority order: first what you specified, then the keys configured in the hub, then model-router:choose-model (if installed); otherwise it inherits the master's settings.
  5. Writes the handoff file outside the hub, starts the child session with the one-line prompt Read and follow <file>, records it as running, and prints a full summary for you.

The detected environment determines how the child session is opened and whether the scope guard can be enabled:

tmuxTMUX is set and tmux is in PATHActive

How a child session is launched

For the master and a child session to exchange messages, they must share the same account and configuration directory (two sessions with different configuration directories cannot talk to each other). If you launch Claude Code through an alias or wrapper that selects a profile or adds flags, child sessions have to start the same way. That's why spawn uses scripts/launch.mjs to inspect how the master was started (identity variables such as CLAUDE_CONFIG_DIR, HOME, and wrapper profile variables, plus configuration flags) and launches every child session with those same parameters, adding the child-specific flags (-n, --model, --effort, --permission-mode, --add-dir for access to the handoff directory) and setting the SESSION_HUB_* role variables.

In tmux, for example, the launch command looks like this:

env SESSION_HUB_ROLE=child SESSION_HUB_MASTER=hub \
  SESSION_HUB_SCOPE_ROOT=/work/hub/product SESSION_HUB_HANDOFF=<dir>/t42-product-handoff.md \
  SESSION_HUB_REGISTRY=<config dir>/session-hub/children-<hub id>.json SESSION_HUB_GUARDS=on \
  claude -n t42-product --model sonnet --effort medium --permission-mode default \
  --add-dir <dir> -- 'Read and follow <dir>/t42-product-handoff.md'

Two operational details are worth noting at launch time:

  • Permission mode: the child session inherits the master's mode, because messages between sessions with mismatched permission-bypass settings would stall waiting for manual confirmation. If the master bypasses permission prompts, spawn asks you on every launch which mode to give child sessions; with Permissions: inherit, it skips the prompt and uses the master's mode.
  • Identity check: after launch, spawn verifies that the child session appears in the session list. If it doesn't, it is running under a different account—spawn withholds the work and alerts you.
  • Worktrees and write root: if the worktree sits inside the repository, the child session creates it and the repository remains its write root; if it sits in a sibling directory, the master creates it before launch and that worktree becomes the write root. That is the only operation the master ever performs on a repository.

Once child sessions are running, all coordination flows through a structured message protocol.

6. Communicating without noise: the five message types

With multiple sessions working in parallel, the master needs concise, structured updates without constantly polling its children. Every child session talks only to the master using a fixed format:

[<task> <repo>] <type>: <text>

Messages sent by the master, in turn, always start with [master]. The master never polls: it updates solely when a message or an idle notification arrives.

TypeWhen it is sentWhat the master does
questionThe child session is blocked on a decisionAnswers directly, or relays the question to you and sends your answer back
out-of-scopeA need or request arises outside the scope (even if you asked for it directly inside the child session)Routes it: asks you to confirm if needed, forwards it to the appropriate child session, starts a new one, or performs a read itself
prA pull request has been opened (the message text carries its URL)Records the URL and applies the hub's pull request rules
doneThe assigned work is finishedApplies the hub's completion rules
abandonedWork was stopped (the text explains why)Notifies you immediately

One security rule is non-negotiable: inter-session messages carry information, never authorization. No session runs merges, pushes, deletions, or settings changes just because another session asked it to. When mods are active, session-hub automatically prepends an explicit reminder line to every incoming message.

Written instructions in the handoff spell out the boundaries, but on their own they don't prevent accidental mistakes. That's where three active guards come in.

7. Three guards: they all fail closed

Three mechanisms enforce each child session's scope. They run only in child sessions and share one conservative rule: every guard fails closed. If a guard cannot verify with certainty that an operation is allowed, it blocks the operation and explains why.

If you need to disable all three for a specific case, set SESSION_HUB_GUARDS=off or put Guards: off in the hub configuration.

The scope guard (hook, works even with mods disabled)

session-hub-scope-guard runs before every Edit, Write, and NotebookEdit. It resolves the target's real path component by component, blocking both a symlink pointing outside the repository and a sibling directory that happens to share the same name prefix.

It also stops any ambiguous or misconfigured case:

  • a relative target path;
  • a write root set to / or to your home directory;
  • a file with more than one hard link: another link to it could live outside the write root, and editing it would modify the file there too;
  • the repository's Claude Code settings, .claude/settings.json and .claude/settings.local.json: their env and hook settings could disable the child session's guards on its next launch, so changes to them must be requested through the master (the shell check blocks them too);
  • an unknown role value or unreadable input;
  • node missing from PATH.

If the check takes too long, an internal watchdog blocks the operation after 7 seconds, ahead of the hook's 10-second timeout.

The shell check (mod, best-effort)

Before a child session runs a Bash or Monitor command, the mod parses it the way bash and zsh would (on macOS, the Bash tool uses zsh) and inspects redirections—including <> and zsh forms such as >!—along with the targets of tee, touch, mkdir, rm, rmdir, truncate, unlink, cp, mv, ln, install, and sed -i, as well as find (with -delete and -fprint, plus the command executed via -exec or -execdir). It also inspects commands inside substitutions ($(…), backticks, <(…), including inside double quotes and in here-documents with an unquoted delimiter) and the literal command string passed to eval or sh -c. It tracks literal cd and pushd calls and blocks any write outside the write root, while still allowing /dev and system temporary directories. It also blocks hard links to files outside the root and writes traversing a symlink created by the same command.

When it cannot parse a command—for instance, a here-document whose delimiter never appears—it blocks the command and explains why. The write root follows the same rules as the scope guard: it must be an existing directory and cannot be / or your home directory.

[session-hub] Shell command blocked: it writes /work/hub/design/notes.md, outside the write root /work/hub/product. Do not retry this write through another command or tool. Send an `out-of-scope` message to the master, saying what you need written and why, and tell the user that you passed the request to the master.

This check is best-effort because it inspects only the literal command line: it cannot evaluate targets hidden in variables, command-substitution output, or globs, nor writes performed internally by an invoked program (a script, git, or a build tool).

The send guard (mod)

To prevent unauthorized sideways coordination, a child session may send messages only to its master (by name) or to its own subagents. Any other recipient—such as a sibling session or a socket address—is blocked with a message directing it back to the master:

[session-hub] This session is a child and may message only its master, "hub". Send what you need to "hub" with your message prefix; a request for another session or repository is an `out-of-scope` message, and the master routes it.

The scope line

In long-running sessions, initial instructions can get compacted or cleared. When mods are active, session-hub keeps the role and scope (in a child session) or the children record (in the master) permanently visible in the system prompt, and re-injects the same text as context on the first turn after startup, after compaction, and after /clear.

8. Checking status: /session-hub and the side panel

To give you a complete view of child sessions without interrupting the agent's work, the mod registers the /session-hub command. Its output is visible only to you and is never sent to the model.

  • In the master, it prints the record path and a summary table of child sessions, and opens the dedicated panel next to the chat. Each row shows the recorded status, live status from the session list, model, effort, and last message; the panel refreshes every 30 seconds and whenever you run /session-hub. The panel uses the same colors as model-router: the model in bold in its tier's color, effort as a four-cell bar (▰▰▰▱ high) in its level's color, and status in green while the session is working, yellow if it is waiting, abandoned, or missing from the session list, and red if it is lost. The command's table includes the bar, without the colors.
  • In a child session, it summarizes the role, write root, handoff file, record, and guard status.

When the master launches child sessions via a Bash command, one line per child appears beneath the command line using the same colors: model, effort, and name, for example ⎿ 🔀 opus ▰▰▰▱ high -> t123-product. The mod reads these from the launch command written by spawn; commands that specify neither model nor effort do not get this line.

Here is sample output from running /session-hub inside a child session:

Role: child of "hub"
Write root: /w/repo
Handoff: /h/t42.md
Children record: not set
Guards: on (scope guard, shell check, send guard)

All data shown by the command and the panel comes from the children record maintained by the master.

9. The children record

To track hub state without cluttering any git repository with temporary files, the master stores a single JSON file per hub outside the hub directory itself:

<config dir>/session-hub/children-<hub id>.json

Here, <config dir> is CLAUDE_CONFIG_DIR or ~/.claude, and <hub id> is the first 16 hex digits of the SHA-256 hash of the hub's real path.

  • What each entry stores: name, repository, task, scope, model, effort, status, start time, last message, and requests.
  • Possible statuses: running, waiting-user, done, abandoned, and lost (recorded as active, but no longer present in the session list).

Skills update this file exclusively through scripts/registry.mjs, atomically and under a lock, preventing corruption under concurrent writes. If the file does not contain valid JSON, the issue is reported without ever overwriting the file; a record error also never blocks new sessions from launching—spawn warns you and continues.

You can inspect the record directly from the terminal as well:

node "<plugin folder>/scripts/registry.mjs" read --hub /work/hub

10. Limitations to keep in mind

Before bringing session-hub into your daily workflow, keep six practical limitations of the current implementation in mind:

  • The shell check is best-effort and tied to mods. It runs only when mods are active; when they are disabled, shell writes are constrained solely by the handoff.
  • The desktop app has no active guards. Its session-launch tool does not accept environment variables, so a child session opened there receives no role variables and relies solely on the handoff.
  • The send guard requires active mods. With mods disabled, a child session can technically send messages to a sibling session: the rule of talking only to the master relies on the written instructions.
  • Resuming a child session requires its variables. If you run claude --resume without prepending the same SESSION_HUB_* variables, the session loses its child role.
  • An externally killed hook lets the write through. The internal 7-second watchdog protects against a slow check, not against a hook forcefully terminated from outside.
  • Trust applies per repository. Launching claude --bg in a repository nested inside an already-trusted hub fails with Workspace not trusted until you open that repository at least once to trust it.
