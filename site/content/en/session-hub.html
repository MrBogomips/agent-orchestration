session-hub

When a piece of work touches multiple repositories, keeping everything in a single session makes it easy to lose both the thread and the boundaries. With session-hub, a master session in the hub spawns child sessions—one per repository—that run in parallel. Each child session gets a written scope, model, and effort, talks only to the master, and forwards anything outside its perimeter back to it. You work in the child session you know; the master coordinates the rest.

Parallel sessions, a single coordinator

Coordinating multiple repositories in a single chat forces you either to move one step at a time or to jump between disconnected windows. Child sessions in a hub flip that model: they are not pipeline stages, but full Claude Code sessions running in parallel, each in its own pane or in the background, with its repository's rules already loaded.

This changes your role during the work:

  • Step in where your expertise is: you can type in any child session, usually the one you know best (design, prototype, or code).
  • The master coordinates the rest: it spawns the other child sessions, receives their messages without polling, routes requests, and alerts you when your decision is needed.
  • Boundaries hold even on your own requests: if you ask a child session for something outside its scope, the request still goes through the master.

What's inside

To orchestrate child sessions and enforce their boundaries without manual intervention, the plugin combines three skills, a hook, a script, and a mod.

You will almost never need to invoke a skill by name. Just ask in your own words—for example, "start a child session in product for T-42", "set up session-hub in this hub", or "what are the child sessions doing?"—and the right skill is loaded. The first step is describing the hub's layout to the master.

Setting up a hub

Before spawning child sessions, the master needs to know which repositories live in the hub, what role each plays, and your launch preferences. Those rules live in the ## Child sessions section of the hub's instruction file: AGENTS.md at the root, or CLAUDE.md when AGENTS.md does not exist.

To create or update it, ask "set up session-hub for this hub": setup inspects the hub, proposes a configuration, and writes it only after you confirm. Every key is optional, with this precedence: what you say in the conversation overrides keys in the file, and keys override the defaults.

Once the hub is configured, the master has everything it needs to decide how to split a task across itself, its subagents, and child sessions.

Deciding: dispatch

Not every operation on a repository calls for a dedicated child session: the master alone can read two files, whereas editing code or interpreting local conventions requires the repository's full environment. In the master, dispatch makes that call.

When a task arrives that touches the hub's repositories, dispatch reads the configuration section, reconciles the children record with live sessions, and identifies the repositories involved (if in doubt, it asks you and never guesses). For each repository, it applies the first matching row:

SituationAction
A child session is already running for that repository and taskMessages that child session ([master] …); does not spawn a second one
Any write to the repositorySpawns a child session via session-hub:spawn
A read that needs the repository's skills or rules to be interpretedSpawns a read-only child session
A broad read whose output is a summary or conclusionDelegates to a read-only subagent of the master
A few known files to readThe master reads them

Past roughly five files—or whenever a repository search or its build tools are needed—the work no longer counts as "a few known files". dispatch shows you the plan in a short table and then starts all child sessions in a single call to spawn, so their handoffs list one another as sibling sessions.

Starting child sessions: spawn

Once it is clear which child sessions are needed, spawn prepares the environment, assigns the scope, and launches each session in five steps:

  1. Resolves the repository and its base branch, then reconciles the children record.
  2. Checks whether an active child session already exists for that repository and task: if it finds one, it sends it the request instead of starting another.
  3. Picks the execution environment, name, worktree, write root, and scope.
  4. Determines model and effort in priority order: what you specified first, then hub keys, then model-router:choose-model (if installed), and otherwise inherits the master's settings.
  5. Writes the handoff file outside the hub, starts the child session with the one-line prompt Read and follow <file>, records it as running, and shows you a summary.

How the child session is launched

For the master and a child session to exchange messages, they must share the same account and configuration directory (two sessions with different configuration directories cannot communicate with each other). That is why a child starts the same way the master was started: spawn carries over session-configuring flags, adds child-specific flags (-n, --model, --effort, --permission-mode, --add-dir for the handoff folder), and sets the role variables. In tmux, the launch command looks like this:

env SESSION_HUB_ROLE=child SESSION_HUB_MASTER=hub \
  SESSION_HUB_SCOPE_ROOT=/work/hub/product SESSION_HUB_HANDOFF=<dir>/t42-product-handoff.md \
  SESSION_HUB_REGISTRY=<config dir>/session-hub/children-<hub id>.json SESSION_HUB_GUARDS=on \
  claude -n t42-product --model sonnet --effort medium --permission-mode default \
  --add-dir <dir> -- 'Read and follow <dir>/t42-product-handoff.md'

Two operational details matter at launch:

  • Permission mode: every child inherits the same mode as the master, because messages between sessions that differ on bypassing permission prompts sit waiting for your approval.
  • Worktrees and write root: a worktree inside the repository is created by the child, and the repository remains the write root; a worktree in a sibling directory is created by the master before launch and becomes the write root. That is the only action the master ever takes in a repository.

Once the child sessions are running, all coordination flows through a fixed message protocol.

Messages and their five types

When multiple sessions run in parallel, the master needs clear updates without constantly polling its children. Each child communicates only with the master using the prefix [<task> <repo>] <type>: <text>, while messages from the master start with [master]. The master never polls: it stays up to date through incoming messages and an idle notification.

TypeSent whenMaster's job
questionthe child is blocked on a decisionanswer it, or relay the question to you and pass your answer back
out-of-scopean out-of-scope need or request comes up, including one you made in the childroute it: ask you if needed, send it to the child that owns that scope, spawn a new child, or perform the read itself
pra pull request has been opened; the text carries its URLrecord the URL and follow the hub's pull-request rules
donethe work is finishedfollow the hub's completion rules
abandonedthe work was stopped; the text states whynotify you

A message between sessions is always information, never authorization: neither side merges, pushes, deletes, or changes settings merely because another session asked it to. When mods are active, session-hub prepends a reminder line to every message received from another session.

Written rules in the handoff describe the boundaries, but on their own they cannot prevent accidental drift—which is where three active guards come in.

Three guards: each one fails closed

Three mechanisms keep each child session inside its scope. All three run only in child sessions and follow the same principle: each one fails closed. If a guard cannot evaluate an operation, it stops it and explains why. You can turn all three off with SESSION_HUB_GUARDS=off or by setting Guards: off in the hub.

The scope guard (hook, works even with mods disabled)

session-hub-scope-guard runs before every Edit, Write, and NotebookEdit. It resolves the target's real path component by component, blocking both a symlink inside the root that points outside and a sibling folder whose name merely starts with the same prefix as the root.

It also blocks any ambiguous or misconfigured case:

  • a relative target;
  • a write root equal to / or the home directory;
  • an unknown role value or unreadable input;
  • a missing node.

If evaluation drags on, the scope guard blocks the operation after 7 seconds, ahead of the hook's 10-second timeout.

The shell check (mod, best-effort)

Before a child runs a Bash or Monitor command, the mod inspects redirections and targets passed to tee, touch, mkdir, rm, rmdir, truncate, unlink, cp, mv, ln, install, and sed -i. It follows literal cd and pushd calls and blocks any target outside the write root, while keeping /dev and system temp directories allowed.

[session-hub] Shell command blocked: it writes /work/hub/design/notes.md, outside the write root /work/hub/product. Do not retry this write through another command or tool. Send an `out-of-scope` message to the master, saying what you need written and why, and tell the user that you passed the request to the master.

This check inspects only the literal command line: it does not evaluate targets hidden inside variables, command substitutions, or globs, nor what an invoked program writes (a script, git, or a build tool).

The send guard (mod)

To prevent unchecked sideways coordination, a child session may message only its master, by name, or its own subagents. Any other recipient—a sibling session or a socket address—is blocked with a message pointing back to the master:

[session-hub] This session is a child and may message only its master, "hub". Send what you need to "hub" with your message prefix; a request for another session or repository is an `out-of-scope` message, and the master routes it.

The scope line

In a long session, initial instructions can fade after context compaction or a reset. When mods are active, session-hub injects role and scope (in a child) or the children record (in the master) into the system prompt, and sends the same text as context on the first prompt after startup, after compaction, and after /clear.

To keep an eye on all child sessions and their status without interrupting the chat, you can use the built-in command and panel.

The command and the children panel

The mod registers the /session-hub command, whose response is visible only to you and is not read by the model. In the master, it prints the path to the children record and the child-sessions table, and opens the children panel next to the chat.

The panel displays one row per child session with its recorded status, live status from the session list, model, effort, and latest message; it refreshes every 30 seconds and whenever you run /session-hub.

When run in a child session, /session-hub summarizes role, write root, handoff, children record, and guard status:

Role: child of "hub"
Write root: /w/repo
Handoff: /h/t42.md
Children record: not set
Guards: on (scope guard, shell check, send guard)

The status shown by the command and the panel is read from the children record maintained by the master.

The children record

To track child sessions without cluttering repositories with state files, the master keeps one JSON file per hub, outside the hub itself, at <config dir>/session-hub/children-<hub id>.json. The configuration directory is CLAUDE_CONFIG_DIR or ~/.claude, while the hub ID is the first 16 hex digits of the SHA-256 hash of the hub's real path.

  • What each entry records: name, repository, task, scope, model, effort, status, start time, latest message, and requests.
  • Possible statuses: running, waiting-user, done, abandoned, and lost (recorded as active, but no longer present in the session list).

Skills update the children record only through scripts/registry.mjs, atomically and under a lock, so two concurrent writes never drop entries. If the file does not contain valid JSON, the problem is reported without ever overwriting the file; a children-record error never stops a launch either: spawn warns you and carries on. You can also inspect the children record from a terminal:

node "<plugin folder>/scripts/registry.mjs" read --hub /work/hub

Before relying on this workflow in a real hub, it pays to know the limits of these mechanisms.

Limitations

  • Shell writes are covered on a best-effort basis, and only with active mods. With mods disabled, a shell write is restrained by the handoff alone.
  • The desktop app has no guards. Its session-launch tool does not accept environment variables, so a child session opened there receives no role.
  • The send guard requires active mods. With mods disabled, messaging a sibling session is still possible; the rule of communicating only with the master relies on written instructions alone.
  • A child session resumed without its variables is no longer a child session. To resume one, prefix claude --resume with the same SESSION_HUB_* variables.
  • A hook terminated from outside lets the write through. The internal 7-second watchdog covers a slow guard, not a hook interrupted from outside.
  • Trust is per repository. Launching claude --bg in a nested repository inside an already trusted hub fails with Workspace not trusted until you open it at least once.
