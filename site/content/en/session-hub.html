session-hub

When a task spans multiple repositories, trying to handle everything in a single session quickly loses focus and blurs boundaries. With session-hub, a master session opened at the hub root launches one or more child sessions — one per repository — that work in parallel.

Each child session receives a written scope, a model, and an effort level, communicates only with the master, and forwards anything outside its perimeter to it. This lets you step directly into the child session for your domain and guide it closely, while the master coordinates everything else.

1. Parallel sessions, one coordinator

Working across multiple repositories in a single chat forces you to move one step at a time or constantly jump between disconnected windows. session-hub flips this approach: child sessions are not just stages in a pipeline, but full Claude Code sessions running in parallel — each in its own pane or in the background — with its repository's instructions, skills, and conventions already loaded.

This setup changes how you work in concrete ways:

  • Step in where your judgment matters: you can enter and type in any child session, usually the one for the repository you know best (the design, the prototype, or the code).
  • The master orchestrates the rest without noise: it launches the other child sessions, receives their updates without continuous polling, routes requests across projects, and brings you in when a human decision is needed.
  • Boundaries always hold: even if you ask a child session directly for something belonging to another repository, the request still goes up to the master instead of crossing the boundary.

On the Ways of working page you will find four progressive examples of how to apply this pattern, from one person wearing two hats to a full AI-mediated product team:

  • 01 · Two hats — Analyst and UI/UX designer in the same person.
  • 02 · Three hats, three repositories — Developer, analyst, and designer across product, design, and prototype.
  • 03 · Pair programming with AI, evolved — Two builder-agent pairs with a master agent between them.
  • 04 · The AI-mediated product team — A Product Manager in the master, an executable prototype in place of mock-ups.

2. What the plugin is made of

To orchestrate child sessions and automatically enforce their boundaries, session-hub combines three skills, a hook, a script, a mod, and a dedicated command:

NameTypeWhat it does
session-hub:dispatchskillRuns on the master side. For each repository it decides whether the master reads directly, delegates to a subagent, or starts a child session; handles incoming messages, routes out-of-scope requests, and holds onto tasks reserved for the master.
session-hub:spawnskillStarts one child session per repository (desktop app, Herdr, tmux, claude --bg, or manual commands) with scope, model, effort, SESSION_HUB_* role variables, and a handoff file, then records it in the children record.
session-hub:setupskillCreates or updates the ## Child sessions section in the hub instruction file, writing it only after your explicit confirmation.
session-hub-scope-guardhookPreToolUse hook on Edit, Write, and NotebookEdit. In a child session it blocks any edit whose real path falls outside the write root.
scripts/registry.mjsscriptReads and updates the children record atomically and safely.
session-hubmodIn a child session it enables the send guard, the shell check, message origin marking, and the scope line. In the master it adds the child sessions panel. Requires mods to be enabled.
/session-hubcommandShows the current session's role and scope; in the master it also summarizes child sessions and opens the panel. Registered by the mod.

In daily use you will almost never need to invoke a skill by name. Just ask in plain language — for example "start a child session in product for T-42", "configure session-hub in this hub", or "what are the child sessions doing?" — and Claude Code automatically loads the right skill.

The first step to helping the master work well is describing how the hub is organized.

3. Configuring a hub

For the master to distribute work sensibly, it needs to know which repositories make up the hub, what role each one plays, and how you prefer to launch sessions. All of this lives in the ## Child sessions section of the hub instruction file: AGENTS.md in the root folder, or CLAUDE.md if AGENTS.md is not present.

You do not need to write this section by hand. Just ask "configure session-hub for this hub": the setup skill inspects the folder, prepares a proposal, and writes it only after your confirmation.

Every key is optional and follows a clear hierarchy: what you state in the conversation overrides the keys in the file, which in turn override the defaults.

With the hub map clear, the master is ready to decide how to route each new task.

4. Deciding who does what: dispatch

Not every operation on a repository justifies launching a dedicated child session: checking two files can be done by the master, whereas writing code or interpreting local conventions calls for the project's full environment. In the master, this decision belongs to the dispatch skill.

When it receives a task involving repositories in the hub, dispatch reads the configuration, reconciles the children record with the sessions actually running, and identifies the repositories involved (asking for confirmation if anything is unclear, never guessing). For each repository it applies the first matching rule:

SituationAction
A child session is already running for that repository and taskSends a message to that child session ([master] …); does not start a second one
Any edit is required in the repositoryStarts a child session with session-hub:spawn
A read requires the repository's skills or rules to be interpretedStarts a read-only child session
A broad read is needed whose output is a summary or conclusionDelegates to a read-only subagent of the master
Only a few already-known files need to be readThe master reads them directly

Beyond roughly five files — or whenever searching the repository or running its build tools is needed — the work no longer counts as "a few known files". Before taking action, dispatch presents the plan to you in a summary table and then launches all required child sessions in a single call to spawn, so that each handoff immediately lists the others as sibling sessions.

5. Launching child sessions: spawn

Once it is clear which child sessions are needed, spawn prepares the environment, defines the scope, and launches them in five ordered steps:

  1. Resolves the repository and its base branch, then reconciles the children record.
  2. Checks whether an active child session already exists for that repository and task: if so, forwards the request to it instead of opening a duplicate.
  3. Determines the execution environment, session name, worktree if any, write root, and read scope.
  4. Selects model and effort in a fixed priority order: first what you specified, then the keys configured in the hub, then model-router:choose-model (if installed), otherwise inherits them from the master.
  5. Writes the handoff file outside the hub, launches the child session with the one-line prompt Read and follow <file>, records it as running, and prints a full summary for you.

The detected environment determines how the child session is opened and whether the scope guard can be enabled:

EnvironmentDetected whenScope guard

HerdrHERDR_ENV is 1 and herdr is in PATHActive
tmuxTMUX is set and tmux is in PATHActive
Terminalclaude --help lists --bgActive
ManualNone of the aboveActive if you run the command as provided

How a child session is launched

For the master and a child session to exchange messages, they must share the same account and config folder (two sessions with different config folders cannot talk to each other). For this reason, spawn launches each child session with the same base parameters as the master, adding the child-specific flags (-n, --model, --effort, --permission-mode, --add-dir to access the handoff folder) and setting the SESSION_HUB_* role variables.

In tmux, for example, the launch command takes this form:

env SESSION_HUB_ROLE=child SESSION_HUB_MASTER=hub \
  SESSION_HUB_SCOPE_ROOT=/work/hub/product SESSION_HUB_HANDOFF=<dir>/t42-product-handoff.md \
  SESSION_HUB_REGISTRY=<config dir>/session-hub/children-<hub id>.json SESSION_HUB_GUARDS=on \
  claude -n t42-product --model sonnet --effort medium --permission-mode default \
  --add-dir <dir> -- 'Read and follow <dir>/t42-product-handoff.md'

Two operational details are worth noting at launch time:

  • Permission mode: the child session inherits the same mode as the master, because messages between sessions with conflicting permission-bypass settings would stall waiting for manual confirmation.
  • Worktree and write root: if the worktree lives inside the repository, the child session creates it and the repository remains its write root; if it is in a sibling folder, the master creates it before launch and that worktree becomes the write root. This is the only operation the master ever performs on a repository.

Once the child sessions are running, all coordination flows through a structured messaging protocol.

6. Communicating without noise: the five message types

With multiple sessions working in parallel, the master needs concise, structured updates without constantly polling the children. Each child session communicates only with the master using the fixed format:

[<task> <repo>] <type>: <text>

Messages sent by the master, in turn, always start with [master]. The master never polls: it updates only when it receives a message or an idle notification.

TypeWhen it is sentWhat the master does
questionThe child session is blocked on a decisionAnswers directly, or forwards the question to you and relays your answer back
out-of-scopeA need or request arises outside the scope (even if you asked for it inside the child session)Routes it: asks you for confirmation if needed, forwards it to the appropriate child session, launches a new one, or performs a read itself
prA pull request has been opened (the text includes its URL)Records the URL and applies the hub's pull request rules
doneThe assigned work is finishedApplies the hub's wrap-up rules
abandonedThe work has been stopped (the text explains why)Notifies you immediately

One security principle is non-negotiable: an inter-session message carries information, never authorization. No session merges, pushes, deletes, or changes settings just because another session asked it to. With mods enabled, session-hub automatically prepends a line to every incoming message stating this explicitly.

The instructions written in the handoff make the boundaries clear, but on their own they cannot prevent an accidental mistake. That is where three active guards come in.

7. Three guards: all fail closed

Three mechanisms enforce the scope of every child session. They run only in child sessions and share a simple, conservative rule: each one fails closed. If a guard cannot determine with certainty that an operation is allowed, it stops it and explains why.

If a particular situation requires disabling all three, you can set SESSION_HUB_GUARDS=off or Guards: off in the hub configuration.

The scope guard (hook, works even with mods disabled)

session-hub-scope-guard runs before every Edit, Write, and NotebookEdit. It resolves the target's real path component by component: this blocks both a symlink pointing outside the repository and an adjacent folder that happens to share the same name prefix.

It also stops any ambiguous or misconfigured case:

  • a relative target path;
  • a write root set to / or the home folder;
  • an unknown role value or unreadable input;
  • node missing from PATH.

If the check takes too long, an internal watchdog blocks the operation after 7 seconds, before the hook's 10-second timeout.

The shell check (mod, best-effort)

Before a child session runs a Bash or Monitor command, the mod inspects redirections and the targets of tee, touch, mkdir, rm, rmdir, truncate, unlink, cp, mv, ln, install, and sed -i. It also tracks literal cd and pushd commands and blocks any write outside the write root, while still allowing /dev and system temporary folders.

[session-hub] Shell command blocked: it writes /work/hub/design/notes.md, outside the write root /work/hub/product. Do not retry this write through another command or tool. Send an `out-of-scope` message to the master, saying what you need written and why, and tell the user that you passed the request to the master.

This check is best-effort because it inspects only the literal command line: it cannot evaluate targets hidden in variables, command substitutions, or globs, nor what an invoked program (a script, git, or a build tool) writes internally.

The send guard (mod)

To prevent unauthorized side-channel coordination, a child session may send messages only to its master (by name) or to its own subagents. Any other recipient — such as a sibling session or a socket address — is blocked with a notice pointing back to the master:

[session-hub] This session is a child and may message only its master, "hub". Send what you need to "hub" with your message prefix; a request for another session or repository is an `out-of-scope` message, and the master routes it.

The scope line

In long sessions, the initial instructions can get compacted or cleared. With mods enabled, session-hub keeps the role and scope (in a child session) or the children record (in the master) visible in the system prompt at all times, and re-sends the same text as context on the first turn after startup, after compaction, and after /clear.

8. Checking status: /session-hub and the side panel

To get a complete picture of child sessions without interrupting the agent's work, the mod registers the /session-hub command. Its output is visible only to you and is not sent to the model.

  • In the master, it prints the path to the children record and a summary table of child sessions, and opens the dedicated panel beside the chat. Each row shows the recorded status, live status from the session list, model, effort, and last message; the panel refreshes every 30 seconds and whenever you run /session-hub.
  • In a child session, it summarizes the role, write root, handoff file, children record, and guard status.

Here is an example of the output of /session-hub run inside a child session:

Role: child of "hub"
Write root: /w/repo
Handoff: /h/t42.md
Children record: not set
Guards: on (scope guard, shell check, send guard)

All data shown by the command and the panel comes from the children record maintained by the master.

9. The children record

To track the hub's state without cluttering any git repository with temporary files, the master saves a single JSON file per hub outside the hub folder itself:

<config dir>/session-hub/children-<hub id>.json

Here <config dir> is CLAUDE_CONFIG_DIR or ~/.claude, while <hub id> is the first 16 hex digits of the SHA-256 hash of the hub's real path.

  • What each entry stores: name, repository, task, scope, model, effort, status, start time, last message, and requests.
  • Possible statuses: running, waiting-user, done, abandoned, and lost (a session recorded as active, but no longer present in the session list).

Skills update the file exclusively through scripts/registry.mjs, atomically and under a lock, preventing corruption during concurrent writes. If the file does not contain valid JSON, the problem is reported without ever overwriting it; moreover, a record error does not block launching new sessions: spawn warns you and continues.

You can also inspect the children record directly from the terminal:

node "<plugin folder>/scripts/registry.mjs" read --hub /work/hub

10. Limits to know

Before bringing session-hub into your daily workflow, keep six practical limits of the current implementation in mind:

  • Best-effort shell check tied to mods. It works only with mods enabled; when they are disabled, shell writes are restrained by the handoff alone.
  • The desktop app has no active guards. Its session-launch tool does not accept environment variables, so a child session opened there receives no role variables and relies solely on the handoff.
  • The send guard requires mods to be enabled. With mods disabled, a child session can technically message a sibling session: the rule to talk only to the master remains enforced only by written instructions.
  • Resuming a child session requires its variables. If you run claude --resume without prepending the same SESSION_HUB_* variables, the session loses its child role.
  • An externally killed hook lets the write through. The internal 7-second watchdog protects against a slow check, not against a hook forcefully terminated from outside.
  • Trust applies per repository. Launching claude --bg in a repository nested inside an already-trusted hub fails with Workspace not trusted until you open that repository at least once to confirm it.
