Ways of working

session-hub is built on one idea: a person works directly in the session whose work they are competent in, and leaves the master to coordinate the other sessions in parallel. Here is what that looks like for one person wearing two or three hats, for two colleagues pairing with agents, and for a whole product team.

The principle behind every scenario

A child is a full Claude Code session, opened in one repository with that repository's instructions, skills and agents loaded. You can type into it like into any session. What makes it a child is the scope it was given at launch: a write root it cannot leave, a master it reports to, and five message types it uses to do so.

So the split of work is natural. You sit in the child that matches your role and steer it closely. The other children run in parallel on their own tasks. When the child you are in needs something outside its repository, even when you ask it yourself, it sends an out-of-scope message to the master, and the master routes it: to the child that owns that repository, to a new child, or to you for a decision.

Messages are information, not authorization. Neither side merges, pushes, deletes or changes settings because another session asked. Approval comes from a person, in that person's session. With mods on, every message from another session carries a line that says so.

1. The double hat: analyst and UI/UX designer

One person carries two roles on the same feature: they write the analysis, and they are responsible for the user experience. The hub holds two repositories, design for the analysis and prototype for a working prototype of the interface.

The person opens the master in the hub and asks for the feature. The master's dispatch skill decides that both repositories will be written, and starts one child in each with a single spawn call, so each child's handoff names the other as a sibling. The person then moves into the design child and writes the analysis with it. Meanwhile the prototype child builds screens from what the analysis already says.

When the analysis changes something the prototype depends on, the design child does not edit the prototype: its scope guard would block the write. It sends an out-of-scope message to the master, which passes it to the prototype child as a [master] follow-up. The person keeps one train of thought, the analysis, and the other hat is worn by a session that reports back.

2. Developer, analyst and UI/UX designer

The same idea with three repositories: design (requirements and analysis), prototype (the interface, built and runnable) and product (the code that ships). One person moves between three roles; three children work in parallel.

Each child loads its own repository's rules: the product child follows the product's testing and branching conventions, the prototype child the prototype's. The hub's Model and Effort keys can give each repository its own default, for example design: opus and product: sonnet, and with model-router installed the grid chooses for the children the keys leave open.

A hub's Scope key lets a child read named paths outside its write root. The product child can be given read access to the design documents and to the prototype, so it builds against them, but it still cannot change them.

## Child sessions
- Repositories:
  - `design/`: requirements, analysis and API documents, base branch `main`
  - `prototype/`: the runnable UI prototype, base branch `main`
  - `product/`: the product code, base branch `develop`
- Model: design: opus; prototype: sonnet; product: sonnet
- Scope:
  - product: `design/docs/`, `prototype/`
- Layout: panes

A section like this is written by session-hub:setup, which proposes values from what it finds in the hub and writes only after your explicit yes.

3. AI pair programming, evolved

Classic AI pair programming is one person and one agent. Here two colleagues with different roles work at the same time on the same piece of work, each in a different session. Each forms a pair, a builder and an agent, and a master agent coordinates the flow between the two pairs.

Say one colleague works on the API in design and the other implements it in product. Each drives their own child directly. When the implementer's child finds that the API document is ambiguous, it sends a question or an out-of-scope message to the master; the master routes it to the design child, where the other colleague sees it and decides. Neither pair edits the other's repository, and neither has to stop to explain context: the message carries it.

How it runs today: one shared host

Today this setup runs on one shared host. Both colleagues attach over SSH to the same tmux or Herdr session on that machine, and each drives their own pane. All the sessions run under that host's Claude Code login.

The reason is how sessions find each other. A child is started the way the master was started, with the same account and configuration folder, because two sessions with different configuration folders cannot message each other. The master hears its children only for sessions on its own machine. So the colleagues share the machine, not a login of their own each.

4. The AI-assisted, AI-mediated product team

This is the scenario the whole design points to: a product team in which every person works with agents, and the agents carry the coordination between people.

The premise: the prototype replaces the hand-made mock-up

Detailed UI/UX mock-ups drawn by hand are costly to make and to keep current. In this team they are replaced by a prototype: a runnable interface built by a child session from the requirements and the design. The UI/UX designer is responsible for the starting Design System and for the Principles & Patterns that both the prototype and the product follow. The prototype is fed by the product manager, the analysts and the designers; the builder consults it, together with the documentation, while building the product.

A day in the team

The product manager asks the master for a weekly view. dispatch decides which repositories the work touches and starts the children. In the design child, the architect drafts a /week API. The API is a shared interface: the product child will build on it and the prototype will call it, so the design child does not just publish it. It sends the proposal to the master, and the master asks the product manager.

The approval is the product manager's, given in the master. A request that changes a shared interface goes to the interface's owner, and the decision goes back to every sibling that uses it: the master sends a [master] follow-up to the prototype and product children. The prototype child wires the new view; the builder, in the product child, reads the approved API document and the running prototype, both within the product child's read scope, and implements the endpoint with the product's own rules and tests.

When a child opens a pull request it sends pr with the link, and done when finished; the master records both in the children record and follows the hub's rules for closing. The product manager follows the whole flow from the children panel, without asking anyone for a status.

What to keep in mind

  • The guards hold the scope, the people hold the decisions. The scope guard blocks file edits outside a child's write root, also with mods off. The send guard and the shell check need mods on; the shell check is best effort.
  • One machine. The master hears children on its own machine, and children use the master's account and configuration folder. Teams share one host today, as in scenario 3.
  • The desktop app has no guard. A child started there gets no role variables, so its scope holds by the handoff alone; spawn says so in its report.
  • Trust is per repository. The first time a child runs in a repository nested in a trusted hub, it may stop at the trust prompt. That prompt is yours to answer.

The mechanics behind all of this are described in session-hub in detail; how each child gets its model is in model-router.
