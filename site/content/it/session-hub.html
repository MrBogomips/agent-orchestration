session-hub

Quando un lavoro tocca più repository, tenere tutto in un'unica sessione fa perdere il filo e i confini. Con session-hub, una sessione master nell'hub avvia sessioni figlie — una per repository — che lavorano in parallelo. Ogni sessione figlia riceve uno scope scritto, un modello e un effort, parla solo con il master e gli inoltra tutto ciò che esce dal proprio perimetro. Tu lavori nella sessione figlia che conosci; il master coordina il resto.

Sessioni parallele, un solo coordinatore

Coordinare più repository in una sola chat costringe a procedere un passo alla volta o a saltare tra finestre scollegate. Le sessioni figlie di un hub rovesciano questo schema: non sono fasi di una pipeline, ma sessioni Claude Code complete che girano in parallelo, ciascuna nel proprio pane o in background, con le regole del proprio repository già caricate.

Questo cambia il tuo ruolo durante il lavoro:

  • Intervieni dove hai competenza: puoi scrivere in qualsiasi sessione figlia, di solito in quella che conosci meglio (il design, il prototipo o il codice).
  • Il master coordina il resto: avvia le altre sessioni figlie, riceve i loro messaggi senza fare polling, smista le richieste e ti avvisa quando serve una tua decisione.
  • I confini reggono anche con le tue richieste: se chiedi a una sessione figlia qualcosa che esce dal suo scope, la richiesta passa comunque dal master.

Di cosa è composto

Per orchestrare le sessioni figlie e far rispettare i loro confini senza interventi manuali, il plugin combina tre skill, un hook, uno script e una mod.

NomeTipoCosa fa
session-hub:dispatchskillLato master. Decide per ogni repository se legge il master, se legge un subagent o se serve una sessione figlia; gestisce i messaggi delle sessioni figlie, smista le richieste out-of-scope e trattiene i compiti riservati al master.
session-hub:spawnskillAvvia una sessione figlia per repository (app desktop, Herdr, tmux, claude --bg o comandi pronti da lanciare) con scope, modello, effort, variabili di ruolo SESSION_HUB_* e file di handoff, poi la aggiunge al registro.

session-hubmodNella sessione figlia attiva la protezione sugli invii, il controllo sulla shell, la marcatura dell'origine e la riga dello scope. Nel master aggiunge il pannello delle sessioni figlie. Richiede le mod attive.

Quasi mai dovrai chiamare una skill per nome. Ti basta chiedere a parole tue — per esempio "avvia una sessione figlia in product per T-42", "configura session-hub in questo hub" o "cosa stanno facendo le sessioni figlie?" — e viene caricata la skill giusta. Il primo passo è descrivere al master la struttura dell'hub.

Configurare un hub

Prima di avviare le sessioni figlie, il master deve conoscere i repository presenti nell'hub, il loro ruolo e le tue preferenze di avvio. Queste regole stanno nella sezione ## Child sessions del file di istruzioni dell'hub: AGENTS.md nella radice, oppure CLAUDE.md quando AGENTS.md non esiste.

Per crearla o aggiornarla, chiedi "configura session-hub per questo hub": setup esamina l'hub, propone una configurazione e la scrive solo dopo la tua conferma. Ogni chiave è facoltativa, con questa precedenza: ciò che dici nella conversazione prevale sulle chiavi del file, e le chiavi prevalgono sui valori predefiniti.

Una volta configurato l'hub, il master ha tutto ciò che serve per decidere come distribuire un task tra sé, i suoi subagent e le sessioni figlie.

Decidere: dispatch

Non ogni operazione su un repository richiede una sessione figlia dedicata: per leggere due file basta il master, mentre per modificare codice o interpretare convenzioni locali serve l'ambiente completo del repository. Nel master, questa scelta passa da dispatch.

Quando arriva un task che tocca i repository dell'hub, dispatch legge la sezione di configurazione, allinea il registro delle sessioni figlie con le sessioni attive e individua i repository coinvolti (se ha dubbi te lo chiede, senza mai tirare a indovinare). Per ciascun repository applica la prima riga che corrisponde:

SituazioneAzione
È già in esecuzione una sessione figlia per quel repository e quel taskInvia un messaggio a quella sessione figlia ([master] …); non ne avvia una seconda
Qualsiasi scrittura nel repositoryAvvia una sessione figlia con session-hub:spawn
Una lettura che richiede le skill o le regole del repository per essere interpretataAvvia una sessione figlia in sola lettura
Una lettura ampia il cui risultato è una sintesi o una conclusioneDelega a un subagent in sola lettura del master
Pochi file noti da leggereLi legge il master

Superati circa cinque file — oppure quando serve una ricerca nel repository o l'uso dei suoi strumenti di build — il lavoro non rientra più nei "pochi file noti". dispatch ti mostra il piano in una breve tabella e poi avvia tutte le sessioni figlie con un'unica chiamata a spawn, così i rispettivi handoff si indicano a vicenda come sessioni sorelle.

Avviare le sessioni figlie: spawn

Una volta deciso quali sessioni figlie servono, spawn prepara l'ambiente, assegna lo scope e avvia ciascuna sessione seguendo cinque passaggi:

  1. Risolve il repository e il suo branch di base, poi allinea il registro delle sessioni figlie.
  2. Controlla se esiste già una sessione figlia attiva su quel repository e quel task: se la trova, le invia la richiesta invece di avviarne un'altra.
  3. Sceglie l'ambiente di esecuzione, il nome, il worktree, la radice di scrittura e lo scope.
  4. Stabilisce modello ed effort in ordine di priorità: prima ciò che hai indicato tu, poi le chiavi dell'hub, poi model-router:choose-model (se installato), altrimenti eredita quelli del master.
  5. Scrive il file di handoff fuori dall'hub, avvia la sessione figlia con il prompt di una riga Read and follow <file>, la registra come running e ti mostra un riepilogo.

La scelta dell'ambiente determina come viene aperta la sessione e se lo scope guard può entrare in azione:

AmbienteRilevato quandoScope guard
App desktopè disponibile uno strumento di avvio sessione come start_sessioninattivo: lo scope è affidato al solo handoff
HerdrHERDR_ENV vale 1 e herdr è nel PATHattivo
tmuxTMUX è impostata e tmux è nel PATHattivo

Come viene lanciata la sessione figlia

Perché master e sessione figlia possano scambiarsi messaggi, devono condividere account e cartella di configurazione (due sessioni con cartelle di configurazione diverse non comunicano tra loro). Per questo una sessione figlia parte nello stesso modo in cui è stato avviato il master: spawn riporta i flag che configurano la sessione, aggiunge quelli specifici della sessione figlia (-n, --model, --effort, --permission-mode, --add-dir per la cartella dell'handoff) e imposta le variabili di ruolo. In tmux, il comando di avvio ha questo aspetto:

env SESSION_HUB_ROLE=child SESSION_HUB_MASTER=hub \
  SESSION_HUB_SCOPE_ROOT=/work/hub/product SESSION_HUB_HANDOFF=<dir>/t42-product-handoff.md \
  SESSION_HUB_REGISTRY=<config dir>/session-hub/children-<hub id>.json SESSION_HUB_GUARDS=on \
  claude -n t42-product --model sonnet --effort medium --permission-mode default \
  --add-dir <dir> -- 'Read and follow <dir>/t42-product-handoff.md'

Due dettagli operativi contano all'avvio:

  • Modalità di permessi: ogni sessione figlia eredita la stessa modalità del master, perché i messaggi tra sessioni che differiscono nell'aggirare le richieste di permesso restano in attesa della tua approvazione.
  • Worktree e radice di scrittura: un worktree dentro il repository viene creato dalla sessione figlia e il repository resta la radice di scrittura; un worktree in una cartella sorella viene creato dal master prima dell'avvio e diventa la radice di scrittura. È l'unica operazione che il master compie mai in un repository.

Avviate le sessioni figlie, tutto il coordinamento passa attraverso un protocollo di messaggi fisso.

I messaggi e i loro cinque tipi

Quando più sessioni girano in parallelo, il master ha bisogno di ricevere aggiornamenti chiari senza dover interrogare di continuo le sessioni figlie. Ogni sessione figlia comunica solo con il master usando il prefisso [<task> <repo>] <type>: <text>, mentre i messaggi del master iniziano con [master]. Il master non fa mai polling: si aggiorna grazie ai messaggi ricevuti e a una notifica di inattività.

TipoInviato quandoCompito del master
questionla sessione figlia è bloccata su una decisionerispondere, oppure girarti la domanda e rimandare indietro la tua risposta
out-of-scopeemerge un'esigenza o una richiesta fuori dallo scope, inclusa una fatta da te nella sessione figliasmistarla: chiedere a te se serve, inviarla alla sessione figlia titolare dello scope, avviarne una nuova o fare la lettura in autonomia
prè stata aperta una pull request; il testo ne contiene l'URLregistrare l'URL e seguire le regole dell'hub sulle pull request
doneil lavoro è terminatoseguire le regole di chiusura dell'hub
abandonedil lavoro è stato interrotto; il testo ne indica il motivoavvisarti

Un messaggio tra sessioni è sempre un'informazione, mai un'autorizzazione: nessuna delle due parti esegue merge, push, cancellazioni o modifiche alle impostazioni solo perché glielo ha chiesto un'altra sessione. Con le mod attive, session-hub aggiunge a ogni messaggio ricevuto da un'altra sessione una riga iniziale che lo ricorda.

Le regole scritte nell'handoff descrivono i confini, ma non bastano da sole a impedire sconfinamenti accidentali: per questo entrano in gioco tre protezioni attive.

Tre protezioni: nel dubbio bloccano tutte

Tre meccanismi mantengono ogni sessione figlia dentro il suo scope. Agiscono tutti solo nelle sessioni figlie e condividono lo stesso principio: nel dubbio bloccano. Se una protezione non riesce a valutare un'operazione, la ferma e spiega il perché. Puoi disattivarle tutte e tre con SESSION_HUB_GUARDS=off oppure impostando Guards: off nell'hub.

Lo scope guard (hook, funziona anche con le mod disattivate)

session-hub-scope-guard gira prima di ogni Edit, Write e NotebookEdit. Risolve il percorso reale della destinazione componente per componente, così blocca sia un link dentro la radice che punta all'esterno, sia una cartella sorella il cui nome inizia solo con lo stesso prefisso della radice.

Blocca inoltre qualsiasi caso ambiguo o mal configurato:

  • una destinazione relativa;
  • una radice di scrittura pari a / o alla cartella home;
  • un valore di ruolo sconosciuto o un input illeggibile;
  • l'assenza di node.

Se la valutazione si prolunga, lo scope guard blocca l'operazione dopo 7 secondi, in anticipo rispetto al timeout di 10 secondi dell'hook.

Il controllo sulla shell (mod, best-effort)

Prima che una sessione figlia esegua un comando Bash o Monitor, la mod ispeziona le redirezioni e le destinazioni di tee, touch, mkdir, rm, rmdir, truncate, unlink, cp, mv, ln, install e sed -i. Segue i cd e i pushd letterali e blocca ogni destinazione fuori dalla radice di scrittura, mentre /dev e le cartelle temporanee di sistema restano consentiti.

[session-hub] Shell command blocked: it writes /work/hub/design/notes.md, outside the write root /work/hub/product. Do not retry this write through another command or tool. Send an `out-of-scope` message to the master, saying what you need written and why, and tell the user that you passed the request to the master.

Questo controllo esamina solo la riga di comando letterale: non valuta destinazioni nascoste in variabili, sostituzioni di comando o glob, né ciò che scrive un programma invocato (uno script, git o uno strumento di build).

La protezione sugli invii (mod)

Per evitare coordinamenti laterali fuori controllo, una sessione figlia può inviare messaggi solo al proprio master, per nome, oppure ai propri subagent. Qualsiasi altro destinatario — una sessione sorella o un indirizzo socket — viene bloccato con un messaggio che rimanda al master:

[session-hub] This session is a child and may message only its master, "hub". Send what you need to "hub" with your message prefix; a request for another session or repository is an `out-of-scope` message, and the master routes it.

La riga dello scope

In una sessione lunga le istruzioni iniziali possono perdersi dopo una compattazione o un azzeramento del contesto. Con le mod attive, session-hub inserisce ruolo e scope (nella sessione figlia) o il registro (nel master) nel system prompt, e invia lo stesso testo come contesto al primo prompt dopo l'avvio, dopo una compattazione e dopo /clear.

Per tenere sotto controllo tutte le sessioni figlie e il loro stato senza interrompere la chat, puoi usare il comando e il pannello integrati.

Il comando e il pannello delle sessioni figlie

La mod registra il comando /session-hub, la cui risposta è visibile solo a te e non viene letta dal modello. Nel master stampa il percorso del registro e la tabella delle sessioni figlie, e apre il pannello delle sessioni figlie accanto alla chat.

Il pannello mostra una riga per ogni sessione figlia, con stato nel registro, stato in tempo reale dall'elenco delle sessioni, modello, effort e ultimo messaggio; si aggiorna ogni 30 secondi e ogni volta che esegui /session-hub.

Eseguito in una sessione figlia, /session-hub riepiloga ruolo, radice di scrittura, handoff, registro e stato delle protezioni:

Role: child of "hub"
Write root: /w/repo
Handoff: /h/t42.md
Children record: not set
Guards: on (scope guard, shell check, send guard)

Lo stato mostrato dal comando e dal pannello viene letto dal registro delle sessioni figlie gestito dal master.

Il registro delle sessioni figlie

Per tenere traccia delle sessioni figlie senza sporcare i repository con file di stato, il master mantiene un file JSON per ogni hub, fuori dall'hub stesso, in <config dir>/session-hub/children-<hub id>.json. La cartella di configurazione è CLAUDE_CONFIG_DIR oppure ~/.claude, mentre l'ID dell'hub corrisponde alle prime 16 cifre esadecimali dello SHA-256 del percorso reale dell'hub.

  • Cosa registra ogni voce: nome, repository, task, scope, modello, effort, stato, ora di avvio, ultimo messaggio e richieste.
  • Stati possibili: running, waiting-user, done, abandoned e lost (registrata come attiva, ma non più presente nell'elenco delle sessioni).

Le skill modificano il registro solo tramite scripts/registry.mjs, in modo atomico e sotto lock, così due scritture concorrenti non perdono voci. Se il file non contiene JSON valido, il problema viene segnalato senza mai sovrascrivere il file; un errore sul registro non ferma comunque un avvio: spawn te lo segnala e prosegue. Puoi consultare il registro anche da terminale:

node "<plugin folder>/scripts/registry.mjs" read --hub /work/hub

Prima di affidarti al flusso su un hub reale, conviene conoscere i confini di questi meccanismi.

Limiti

  • Le scritture da shell sono coperte in modalità best-effort, e solo con le mod attive. Con le mod disattivate, una scrittura da shell è trattenuta dal solo handoff.
  • L'app desktop non ha protezioni. Il suo strumento di avvio sessione non accetta variabili d'ambiente, quindi una sessione figlia aperta lì non riceve alcun ruolo.
  • La protezione sugli invii richiede le mod attive. Con le mod disattivate è ancora possibile inviare messaggi a una sessione sorella; la regola di comunicare solo con il master resta affidata alle sole istruzioni scritte.
  • Una sessione figlia ripresa senza le sue variabili non è più una sessione figlia. Per riprenderla, anteponi le stesse variabili SESSION_HUB_* a claude --resume.
  • Un hook terminato dall'esterno lascia passare la scrittura. Il watchdog interno di 7 secondi copre una protezione lenta, non un hook interrotto da fuori.
  • Il trust vale per singolo repository. Avviare claude --bg in un repository annidato dentro un hub già attendibile fallisce con Workspace not trusted finché non lo apri almeno una volta.
