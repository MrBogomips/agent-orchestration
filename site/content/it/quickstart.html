Guida rapida

Partiamo da zero fino ad avere un hub con due sessioni figlie che lavorano in parallelo e le prime decisioni di routing sullo schermo. Ogni passaggio ti dice cosa dovresti vedere, così sai che tutto ha funzionato prima di andare avanti.

Requisiti

RequisitoValore
Claude Code, per le mod2.1.329 o successiva; entrambi i plugin dichiarano engines["claude-code"]: ">=2.1.329" e sono stati testati sulla 2.1.329 e 2.1.330

Le skill e l'hook a protezione dello scope funzionano anche con le mod disattivate. Perdi però le protezioni sui messaggi e sui comandi shell, il pannello, il routing all'avvio dei subagent, le misurazioni ed entrambi i comandi.

Installazione dal marketplace

Entrambi i plugin si trovano nel marketplace mrbogomips. Da dentro Claude Code:

/plugin marketplace add MrBogomips/claude-plugins
/plugin install session-hub@mrbogomips
/plugin install model-router@mrbogomips

Oppure dal terminale:

claude plugin marketplace add MrBogomips/claude-plugins
claude plugin install session-hub@mrbogomips
claude plugin install model-router@mrbogomips

Ogni plugin funziona anche da solo. Se li installi entrambi, session-hub:spawn carica model-router:choose-model per scegliere il modello e l'effort di ogni sessione figlia; senza model-router, la sessione figlia eredita modello ed effort del master, e spawn lo segnala nel suo report.

Controlla che le mod siano attive

Digita /session-hub o /model-router. Se Claude Code non riconosce il comando, la mod non è caricata: o le mod sono disattivate, oppure la versione di Claude Code è precedente alla 2.1.329 (controlla con claude --version). In una sessione senza ruolo nell'hub, /session-hub risponde:

session-hub: This session has no session-hub role. It becomes a master when it uses session-hub:spawn or session-hub:dispatch.

Configura un hub

Un hub è una cartella qualsiasi che raccoglie diversi repository git, come sottocartelle o submodule. Apri Claude Code nella cartella radice e chiedi in linguaggio naturale:

set up session-hub for this hub

session-hub:setup analizza l'hub (sottocartelle con .git, .gitmodules, il branch di base di ogni repository, le regole per i worktree), propone una sezione ## Child sessions per il file AGENTS.md (o CLAUDE.md) dell'hub, te la mostra e la scrive solo dopo una tua conferma esplicita. Non esegue commit. Ogni chiave è facoltativa: senza questa sezione, spawn usa i valori predefiniti e nel report ti propone di eseguire setup.

Tieni gli hub di test dentro la tua cartella home. Durante i test, un hub messo nella cartella temporanea di sistema non caricava alcun file di istruzioni del progetto.

Il tuo primo spawn

Se puoi, avvia il master dentro Herdr o tmux: in questo modo spawn apre ogni sessione figlia in un pane accanto al tuo, con la protezione dello scope attiva. Chiedi un'attività che tocca due repository:

T-42: add GET /export to product (CSV, at most 10 000 rows) and document the limit in design/docs/api/export.md.

Si carica dispatch, dichiara la sua decisione in una breve tabella (una sessione figlia in scrittura per product, una per design), poi chiama spawn una sola volta per entrambe, così ogni handoff cita l'altra come sessione sorella. Il report elenca per ogni sessione figlia il nome, il repository, la radice di scrittura, il modello e l'effort, l'ambiente, come aprirla ed eventuali avvertenze.

Primo avvio in un repository. L'autorizzazione della cartella non si propaga automaticamente ai repository annidati dentro un hub già autorizzato. Una sessione figlia potrebbe fermarsi al prompt di autorizzazione nel proprio pane, mentre claude --bg fallisce con l'errore Workspace not trusted. Rispondi al prompt (oppure apri il repository una volta con claude) e poi fai riprovare il master.

Controlla le sessioni figlie: /session-hub

Nel master, /session-hub mostra il percorso del registro e una tabella delle sessioni figlie: stato nel registro, stato in tempo reale dall'elenco delle sessioni, modello ed effort, ultimo messaggio. Apre anche il pannello delle sessioni figlie accanto alla chat, aggiornato ogni 30 secondi. In una sessione figlia, lo stesso comando ne mostra il ruolo, la radice di scrittura, l'handoff e indica se le protezioni sono attive.

La tua prima decisione di routing

Con model-router installato, choose-model entra in gioco ogni volta che l'agente sta per avviare un subagent. Chiedi un'operazione che ne richieda uno, ad esempio una ricerca su un repository di grandi dimensioni. Prima dell'avvio, l'agente scrive una riga:

🔀 haiku ▰▱▱▱ low -> find callers of parseConfig, easy to check

La riga indica: il modello, una barra dell'effort da quattro tacche (da una per low a quattro per xhigh), l'effort e il motivo in meno di dodici parole. Con la mod attiva, la stessa riga compare a colori sotto la chiamata Agent, con il modello e l'effort effettivamente assegnati al subagent dopo il routing:

⏺ Agent([mr:read-search] Find the CSV writer)
  ⎿  🔀 haiku  ▰▱▱▱ low    -> judge: read-search; lowered from sonnet

Più chiamate Agent effettuate in uno stesso messaggio vengono raggruppate in un'unica riga "background agents launched"; premi ctrl+o per espandere ogni chiamata con la relativa riga.

Consulta le misurazioni: /model-router

/model-router apre la vista d'uso sulla scheda Overview, ultimi 7 giorni, a livello utente. Con Tab e Shift+Tab ti sposti tra Overview, Models, Classes e Decisions; d, w, m, a selezionano l'intervallo temporale; p alterna tra i tuoi dati globali e quelli del progetto corrente; o genera e apre la pagina del report; Esc chiude la vista.

Non aspettarti numeri fin da subito. Un'attività viene conteggiata solo quando si chiude la sua finestra di rilavorazione, cioè 30 minuti dopo il report del subagent oppure a fine sessione. In una sessione reale puoi vedere cosa aspettarti dopo un giorno, una settimana e un mese.

Registra le eccezioni di un progetto: model-router:setup

In un progetto in cui certe attività richiedono più di quanto assegni la griglia, o in cui basta meno, chiedi:

set up model routing for this project

model-router:setup ti chiede quali valori predefiniti ed eccezioni vuoi impostare, ne suggerisce alcune analizzando il repository (migrazioni, infrastruttura, fatturazione, codice generato, refactoring massivi), ti mostra la sezione ## Model routing esatta e la scrive nel file AGENTS.md del progetto solo dopo un tuo sì esplicito. Trovi tutti i dettagli nella pagina di model-router.
